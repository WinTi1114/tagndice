# 태그 앤 다이스 캐릭터 시트 — 설계 스펙 (2026-08-10 26차 개정)

## 기준 규칙 (사이트 최신 규칙 채택, 기획 시트의 구 능력치 시스템은 미채택)

### 세계관 톤
낭만과 환상의 세계. 종족 예: 엘프, 인간, 드워프, 하플링, 수인, 설인, 골렘, 유령, 이세계인 등 자유 상상.

### 캐릭터 생성 순서
1. 태생 태그 결정 (종족/배경/본능 3개 고정, 고정 1등급, 모든 판정에 상시 적용 — 레벨 합산에는 미포함, 15차 개정)
2. 경험 태그 결정 (지식/기능, 총 3포인트 배분, 최대 10개까지 확장 가능)
3. 최대 체력 결정 (기본 5칸)
4. 이름/자기소개

### 자원 3종 (능력치 없음)
- 체력: 시작 5칸, 레벨업으로 증가. 피해를 받을 때마다 체력 칸 하나에 "상처"를 표시(구체적 묘사는 자유). 상처 자체는 행동 페널티 없음 — 모든 칸이 상처로 가득 차면 즉시 행동불능(→사경 판정).
- 정신력: 시작 3. 지적 행동(지식과 사고를 활용하는 행동)에 사용.
- 피로도: 시작 3. 신체적 행동(신체 움직임과 기능을 활용하는 행동)에 사용.

### 컨디션 (정신력 · 피로도)
정신력·피로도를 묶어 "컨디션"이라 부름. 태그 선언에는 컨디션 1점을 소모.
태그의 종류(지식/기능)만으로 어떤 컨디션이 소모되는지 기계적으로 정해지지 않음 — 같은 태그라도 플레이어가 어떻게 행동을 묘사하느냐에 따라 소모되는 컨디션이 달라질 수 있고, 최종적으로는 플레이어의 묘사·RP를 바탕으로 마스터가 판단.

### 판정
2d6 → 10+(거의 문제 없이 성공, 아무 방해 없이 행동) / 5~9(하기는 하나 일이 꼬임 — 침식 태그 효과 발생 또는 GM 지정 위험) / 4-(GM 재량, 보통 실패하거나 더 큰 문제 발생)
태그 선언: 관련 자원 1점 소모 → 판정 없이 자동 성공 (자원 고갈 시 불가)
태그와 무관한 시도: 피로도 1점 강제 소모 + 불리, 대성공도 강등

### 태그 등급 & 레벨
1등급(견습)/2등급(숙련)/3등급(달인)
레벨 = 경험 태그 등급 합만: Ⅰ(1~5) Ⅱ(6~10) Ⅲ(11~15) Ⅳ(16~20) Ⅴ(21+)
※ **15차 개정 — 계산식 자체를 수정.** 14차에서는 라벨만 "장점 태그 등급 합"→"경험 태그 등급 합"으로 바꾸고 실제 계산(태생 고정 +3 + 경험 태그 등급 합)은 그대로 두었으나, 이는 14차에 남겨둔 미확인 사항이었음. 사용자가 GPT로 만든 별도 프로토타입(index.html)을 공유했는데, 그 코드가 독립적으로 "레벨 = 경험 태그 등급 합만(+3 없음)"으로 구현되어 있었고, 확인 결과 이 쪽이 실제 의도한 규칙으로 확정됨. 이유: +3을 포함하면 시작 캐릭터(경험 태그 3P 배분)가 곧바로 레벨 Ⅱ(3+3=6)로 시작하게 되어 "시작은 레벨 Ⅰ"이라는 통상적 기대와 어긋남 — +3을 빼면 시작 캐릭터는 레벨 Ⅰ(경험 합 3)로 자연스럽게 시작함. 이에 따라 태생 태그는 더 이상 "장점 태그"(=레벨에 반영되는 태그)가 아니라 "상시 적용되는 고정 효과"로 재정의(용어 "장점 태그"는 이제 경험 태그만 지칭하는 셈이라 혼동 방지를 위해 문서 전반에서 사용을 줄임). PDF·엑셀·웹 프로토타입 3곳 모두 이 계산식으로 통일함 (엑셀 수식에서 `+3` 제거, PDF는 애초에 손으로 적는 칸이라 표시 텍스트에 +3 언급이 없어 변경 불필요, 웹 프로토타입은 원래부터 정답이었으므로 라벨만 "장점"→"경험"으로 통일).
레벨업: 체력/정신력/피로도 중 1개 최대치 +1

### 침식 태그
사경 판정(2d6, 동일 표) 5~9 결과로 영구 서사적 부작용 획득. 4-는 사망.
최대 3개까지 보유 가능. 이미 3개 보유한 상태에서 다시 행동불능 판정을 하게 되면 굴림 없이 곧장 사망(4- 결과와 동일 처리).
정화: 레벨업할 때마다 침식 태그 하나를 지울 수 있음.

### 야영 (구 "휴식" 명칭 대체)
제대로 자리 잡고 쉴 때: 일행 중 1인이 보급품/식량 1회분 소비.
- 짧은 휴식: 정신력 또는 피로도 중 하나만 선택하여 전부 회복
- 긴 휴식: 정신력과 피로도 모두 전부 회복
- 치료: 상처 치료에 도움이 되는 경험 태그를 선언하면 상처 하나 제거(= 체력 1칸 회복) — 2026-08-09 사용자가 "상처 칸" 정의를 확정 답변하여 확인 완료.

### 장비 & 소지품 태그 (태그 기반, 고정 인벤토리 없음)
- 착용 장비(무기·방어구): 기본 태그 느림/무게n/식량/양손/착용, 무기: 물리|마법 피해+n, 방어구: 방어n/방어+n(중첩시 최고값만). 소지품 한도에 포함 안 됨.
- 소지품 태그: 몸에 지니고 다니는 의미 있는 물건(귀중한 전리품, 유물, 특수한 재료 등)은 [소지품] 태그로 취급. 경험 태그와 완전히 별도의 자리이며 최대 10개까지 보유 가능.
  - 착용 중인 장비(무기·방어구)와 마법 물품은 이 한도에 포함되지 않음.
  - 사소하고 대수롭지 않은 물건(약간의 여비, 기본적인 야영 도구 등)도 포함되지 않음 — 태그로 적어둘 만큼 의미 있는 것만 자리를 차지.
  - 자리가 다 찬 상태에서 새 소지품을 갖고 싶다면 기존 소지품 태그 하나를 버리거나 놓고 가야 함. 내려놓는 건 그 자리에서 즉시 가능.
  - 이 규칙은 몸에 지니고도 의미 있게 행동할 수 있는 물건에만 적용 — 커다란 바위처럼 짊어진 채로는 별다른 행동이 불가능한 경우는 이 규칙과 별개로 마스터가 판단.
※ 하중 한계 개념 없음 (소지 무게 제한 없음)

### 화폐 (2단계 체계)
- 동화/은화/금화: 일상적인 경제. 몬스터·마법과 무관한 모든 거래에 사용.
- 조각: 몬스터에게서 갈무리한 특수 화폐. 몬스터나 마법의 힘이 얽힌 거래에만 사용.
- 환율: 1금 = 10은 = 100동
- 가격 기준: 평민 노동자의 하루 일당 = 1금. 모든 가격은 이 기준에서 역산.

### 마법 물품
캐릭터마다 자신의 정체성을 상징하는 특별한 마법 물품 하나를 제작.
- 형태: 무기류 / 방어구류 / 마법도구류 중 하나
- 물품 이름 + 전용 태그를 정함
- 전용 태그는 캐릭터의 다른 태그와 유일하게 중첩 가능 — 자신의 경험 태그로 판정/선언할 때 물품 태그를 함께 걸어 두 효과를 하나의 묘사로 엮을 수 있음
- 사용 제한: 세션당 총 3회, 자신의 차례에 1회만 발동 가능

## 레이아웃

### 앞면 — 액션 카드
로고 배너 / PC이름 / 레벨(Ⅰ~Ⅴ, 자동계산, 노치 배너형 배지) · 태생 태그 3칸(종족/배경/본능, 각 카드 우측에 육각 등급 배지 "1") · 자원 트랙(체력♥/정신력✦/피로도◐, 각 아이콘 배지 + 시작치 표시) · 경험 태그 표 10행(지식|기능, 등급) · 핵심 자원 + 판정표(2d6 10+/5~9/4-) + 규칙 설명 박스 3개(태그선언/컨디션/상처) · 침식 태그(카드형 3행, 각 카드에 해골☠ 배지) · 마법 물품(이름/형태/전용태그/세션당 사용 3회 트래커) · 장비 & 소지품(소지품 태그 표 10행, # + 태그 1줄 · 경험 태그와 별개 슬롯 안내문) + 하단 6칸 필드(착용 무기/착용 방어구/금화/은화/동화/조각)

### 11차 개정 — 소지품 태그 시스템 신설 + 뒷면 초상화·백스토리 병합
사용자 피드백 1: "짐칸이 너무 적어" + 소지품 태그 규칙 전문 제공(경험 태그와 별개 슬롯, 최대 10개, 착용 장비·마법 물품·사소한 소지품 제외, 자리가 다 차면 기존 태그를 버리고 즉시 교체 가능).
- 기존 "장비 & 소지품" 3열 표(물품이름/태그/수량, 5행)를 폐지하고 "소지품 태그" 2열 표(#/소지품 태그, 10행)로 교체 — 최대 10개 규칙과 행 수를 정확히 일치시킴.
- "착용 무기"·"착용 방어구" 필드를 신설해 소지품 한도에 안 걸리는 착용 장비를 별도로 명시. 공간 확보를 위해 화폐(금/은/동/조각) 필드와 한 줄로 통합(하단 6칸 필드 행).
- PDF 공간 확보를 위해 트리밍: 핵심자원 행간격 4mm→3mm, 태그선언/컨디션/상처 설명 박스 패딩·줄간격 축소, 침식 태그 카드 높이 10mm→8mm, 마법 물품 박스 패딩 축소, 소지품 표 행간 패딩 축소. 트리밍 후에도 배지 스타일(10차 개정)은 시각적으로 그대로 유지됨.
- 엑셀: 동일 구조로 반영 — "착용 장비 & 소지품 태그" 섹션(무기/방어구 필드 + #/소지품 태그 10행 표 + 화폐), 소지품 규칙 설명은 note()로 표 위에 배치.
- 오버플로우 검증: 10행 표 적용 첫 시도에서 실제로 페이지 1 내용이 페이지 2(뒷면 헤더)로 겹쳐 흐르는 오버플로우 발생 확인(스크린샷) → 위 트리밍 적용 후 재검증, `pdfinfo` "Pages: 2" + 앞뒷면 래스터 스크린샷으로 겹침 해소 및 하단 여백 확보 확인.

사용자 피드백 2: "뒷면 백스토리 카드 공백이 신경쓰임. 초상화 부분이랑 백스[토리] 부분을 합쳐줄 순 없을까?"
- 기존 3열 그리드(초상화+기본정보 47mm 컬럼 | 백스토리 1fr 컬럼 | GM메모 30mm 컬럼)를 2열 그리드(통합 패널 1fr | GM메모 30mm)로 재구성.
- 통합 패널(`.story-panel`) 내부: 상단에 초상화(40mm 정사각) + 기본정보 필드를 가로로 배치, 구분선 아래로 "상세 백스토리" 자유 서술 공간이 남은 높이를 전부 차지 — 두 요소가 하나의 테두리 안에 들어와 예전처럼 "작은 정사각형 박스 + 뚝 떨어진 거대한 빈 박스"로 보이던 문제 완화. 백스토리 영역 자체의 가용 폭도 넓어짐(기존 47mm+1fr 분할 → 통합 1fr).
- GM 비밀 메모 컬럼은 변경 없음.

### 12차 개정 — 초상화 박스 확대
사용자 피드백: "PDF 파일 초상화 칸이 너무 작은거 같아." 11차 개정 때 병합하며 정한 초상화 크기(40mm 정사각)가 넓어진 패널 폭 대비 작아 보인다는 지적. `.portrait.sp` 폭을 40mm → **60mm**로 확대(높이는 aspect-ratio:1/1로 자동 연동). 기본정보 필드는 옆에서 세로 중앙 정렬 유지, 백스토리 서술 공간은 여전히 넉넉하게 남음. `pdfinfo` "Pages: 2" + 뒷면 스크린샷으로 확인, 오버플로우 없음.

### 10차 개정 — 아이콘 배지 스타일 도입 (참고 이미지 기반, 앞면 한정)
사용자가 던전 배시류 흑백 라인아트 캐릭터 시트 이미지를 레퍼런스로 제시, "한 페이지로 압축하는 느낌"을 요청. 확인 결과 (1) 적용 범위 = 앞면(액션 카드)만, 뒷면은 그대로 유지 / (2) 화풍 = 레퍼런스의 흑백 라인아트 톤은 도입하지 않고 지금의 다크 판타지 톤(크림+보르도+골드)을 유지하며 "배치 밀도"와 "아이콘형 라벨" 구조만 차용.
- 레벨 표시를 노치 코너 배너(육각 배지와 유사한 CSS clip-path) 형태로 재구성.

- 핵심 자원(체력/정신력/피로도) 각 라벨 앞에 육각 아이콘 배지 추가 (체력♥ · 정신력✦ · 피로도◐) — 기존 체크박스 트랙(상처 표시용)은 그대로 유지.

- 일러스트 자산(코너 기어 그림 등)은 제작하지 않음 — 순수 CSS(clip-path 육각형/노치)와 유니코드 글리프(♥ ✦ ◐ ☠)만으로 구현, 기존 폰트·색상 시스템 재사용.
- 엑셀 템플릿은 변경하지 않음 — 이번 변경은 인쇄 카드의 시각적 밀도 문제이며, 스프레드시트 구조상 육각 배지 표현이 부적합하다고 판단.
- 검증: `pdfinfo` "Pages: 2" 확인 + 앞/뒷면 래스터 스크린샷으로 배지 렌더링(테두리, 텍스트 중앙 정렬)과 페이지 오버플로우 여부 육안 확인 완료.

### 15차 개정 — 룰 동기화 + 기능 3종 추가 + 버그 2건 수정
사용자 요청: "GPT로 만든 프로토타입인데, 여기서 더 세부적으로 기능 추가하거나 업데이트를 하고 싶어." AskUserQuestion으로 우선순위 확인 후 진행.

- **레벨 계산식 정정**: 위 "태그 등급 & 레벨" 절 참고 — 프로토타입 쪽이 원래부터 정답(경험 태그 합만)이었고, PDF·엑셀 쪽을 여기 맞춰 수정. 웹 버전은 라벨만 "장점 태그 등급 합"→"경험 태그 등급 합"으로 통일.
- **소지품 태그 규칙 동기화**: "장비 & 소지품" 패널에 착용 장비·마법 물품 제외 캡션과 소지품 규칙 설명문(사용자가 11차에서 준 규칙 전문 요약)을 추가. 화폐를 단일 텍스트 필드에서 금화/은화/동화/조각 4개 필드로 분리(PDF·엑셀과 구조 통일).
- **GM 전용 정보 보호**: 기존에는 "GM 전용·마스터 비밀" 메모가 플레이어 시트 화면 안에 그대로 노출되는 구조였음(같은 파일·같은 화면 전환이라 플레이어가 그냥 GM 세션 탭을 눌러도 다 보임) → GM 메모를 플레이어 시트에서 완전히 제거하고 GM 세션 대시보드로 이동(현재 선택된 캐릭터 기준으로 GM 메모 표시). 추가로 GM 세션 탭 자체에 PIN 잠금 기능 신설(GM 세션 진입 시 PIN 요구, 맞을 때까지 대시보드 진입 불가 — 브라우저 새로고침 시 다시 잠김).
- **여러 캐릭터 슬롯 관리**: 기존에는 GM 대시보드에서만 PC를 추가/전환할 수 있었음 → 플레이어 시트 화면에도 캐릭터 선택 드롭다운 + "새 캐릭터 추가"/"삭제" 버튼 신설. 내부적으로 GM 대시보드와 동일한 `db.pcs`/`db.activeId` 데이터를 공유하므로 중복 로직 없이 재사용.
- **인쇄·이미지 내보내기**: "인쇄 / PDF 저장" 버튼(`window.print()` + `@media print` 스타일 — 내비게이션/버튼/GM 화면은 인쇄 시 자동 숨김) 및 "이미지 저장" 버튼(html2canvas CDN 라이브러리로 PNG 다운로드, 오프라인 등으로 라이브러리 로드 실패 시 안내 문구와 함께 인쇄 버튼 사용을 권하도록 예외 처리).
- **(발견 및 수정) 캐릭터 전환 시 데이터 오염 버그**: 원본 프로토타입의 `save()`가 항상 `collect()`(현재 화면의 입력값을 현재 활성 캐릭터에 기록)를 먼저 실행한 뒤 저장하는 구조였는데, `setActive()`/`addPC()`/삭제 로직이 "활성 캐릭터를 바꾼 다음 save() 호출" 순서였음 — 즉 화면이 아직 새로 그려지기 전(옛 캐릭터의 값이 그대로 표시된 상태)에 그 값을 방금 바뀐 새 활성 캐릭터에 덮어써버리는 구조적 버그. 실제로는 "캐릭터를 전환할 때마다 이전 캐릭터의 입력값이 새 캐릭터(또는 그 반대)에 섞여 저장됨"이라는 심각한 데이터 오염으로 이어짐. `persist()`(저장+재렌더링만, `collect()` 없음)를 별도로 분리하고, 활성 캐릭터를 바꾸는 세 곳(`setActive`/`addPC`/`deleteCharacterById`)은 전환 후 `save()` 대신 `persist()`를 쓰도록 수정 — Playwright로 "캐릭터 A에 데이터 입력 → 캐릭터 B 추가 → A로 복귀 → 데이터 유지 확인" 시나리오를 직접 재현해 검증.
- **(발견 및 수정) 침식 태그/소지품 태그 입력이 실제로는 저장되지 않던 버그**: 원본 코드가 이 두 입력의 `oninput`/`onclick` 핸들러 문자열 안에서 `renderPlayer()`의 지역 변수 `p`를 그대로 참조하고 있었음(`oninput="p.erosion[0]=this.value;save()"` 형태) — 인라인 HTML 이벤트 핸들러는 전역 스코프에서 실행되므로 `p`가 정의되지 않아 브라우저 콘솔에 `ReferenceError: p is not defined`가 발생하며 조용히 실패, 입력한 값이 화면엔 보여도 실제 데이터·저장소에는 전혀 반영되지 않았음(소지품 태그는 이번 세션에서 새로 강조한 핵심 규칙이라 특히 중요). `editErosion(i,v)`/`clearErosion(i)`/`editInventory(i,v)` 전역 함수를 신설해 매번 `current()`를 새로 조회하도록 수정(기존 `editTag()`와 동일한 안전한 패턴). Playwright로 값 입력 → 내부 데이터 모델 반영 확인 + "정화" 버튼 클릭 → 실제로 지워지는지까지 검증.
- **검증**: Playwright로 브라우저를 직접 띄워 레벨 계산(그레이드 3짜리 태그 3개 → 합 9 → 레벨 Ⅱ, 구 계산식이었다면 12→Ⅲ이 됐을 것), 캐릭터 추가/전환/삭제, GM 잠금(오답 PIN 차단 확인 + 정답 PIN 통과 확인, 새로고침 후에도 잠김 유지), 침식·소지품 입력 반영, 인쇄 스타일(내비게이션·GM 화면 숨김 확인) 순서로 전부 확인. 이미지 내보내기는 샌드박스 환경의 외부 CDN 차단으로 실제 다운로드까지는 검증 못 했으나, 라이브러리 로드 실패 시 대체 안내가 뜨는 것까지는 확인.
- 데이터 마이그레이션: 기존 localStorage에 저장된 구버전 데이터(단일 `money` 필드 등)는 새 필드(`gold`/`silver`/`copper`/`shard`)가 빈 값으로 초기화됨 — 프로토타입 단계라 기존 데이터 자동 이전 로직은 만들지 않음.

### 16차 개정 — 삭제 버튼 미작동 + 태그 타이핑 끊김 수정, 캐릭터 초기화 버튼, 레벨업 버튼 신설
사용자 피드백(5건, 순서대로): "캐릭터 삭제 버튼이 제대로 작동을 안해." / "캐릭터 초기화 버튼이 있으면 좋겠어." / "태그 입력 타이핑이 원활하지가 않아." / "핵심 자원 최대치 올리는건 레벨업 시에만 가능하게 해주고." / "레벨업 조건 달성할 때마다 레벨업 버튼을 누를 수 있게 추가하면 좋겠어."

- **원인 진단 — 타이핑 끊김**: 경험 태그·침식 태그·소지품 태그 입력창들이 `oninput`마다 `save()`→`renderAll()`을 타면서 해당 컨테이너의 `innerHTML`을 통째로 재생성하고 있었음. DOM 노드가 매 키 입력마다 파괴·재생성되니 포커스가 즉시 날아가고(한 글자 치면 포커스 이탈, 다시 클릭해야 다음 글자 입력 가능), 한글 조합 입력 중간에 끊길 위험도 있었음. **수정**: "구조적 렌더"(캐릭터 전환 시에만 행 목록 DOM을 새로 그림 — `renderExperienceRows`/`renderErosionRows`/`renderInventoryRows`)와 "값만 저장"(타이핑 시 — `editTag`/`editErosion`/`editInventory`가 모델 갱신 + `localStorage` 저장만 하고 DOM은 건드리지 않음, 이미 화면엔 입력한 값이 그대로 있으므로 다시 그릴 필요가 없음)을 분리. 이름/배경/백스토리 등 일반 입력 필드도 `saveField()`(경량 저장, 재렌더링 없음)로 통일해 전반적인 타이핑 반응성 개선.
- **원인 진단 — 삭제 버튼 미작동**: `deleteCharacterById`가 `confirm()`으로 삭제 여부를 물었는데, 이 파일이 Cowork 대화 안에서 인라인 미리보기(iframe)로 먼저 보여지는 경우 샌드박스 정책상 `window.confirm`/`prompt`/`alert`가 조용히 차단되고 즉시 취소(false/null)로 처리될 수 있음 — 사용자 입장에선 "삭제를 눌렀는데 아무 일도 안 일어남"으로 보였을 것. **수정**: 네이티브 다이얼로그를 전부 없애고, 시트 톤에 맞춘 커스텀 모달(확인/선택/입력/알림, `showModal()`)로 교체 — 어떤 렌더링 컨텍스트(iframe 미리보기든 일반 브라우저 탭이든)에서도 동일하게 동작. `mode()`(GM PIN 확인)·`toggleGmLock()`·`deleteCharacterById()`·`resetCharacter()`(신규)·`levelUp()`(신규)·`importData()` 전부 이 모달을 사용하도록 변경.
- **캐릭터 초기화 버튼 신설**: 캐릭터 바(내 캐릭터 선택 드롭다운 옆)에 "초기화" 버튼 추가 — 같은 슬롯(id 유지)에서 이름·태그·자원·백스토리 등 전부를 빈 캐릭터로 되돌림. "삭제"(슬롯 자체를 없앰, 최소 1개는 남아있어야 함)와 구분되는 별개 동작.
- **핵심 자원 최대치 = 레벨업 전용**: 기존에 자원 행마다 있던 자유 "최대 +1" 버튼을 제거(대신 "최대치 N/10 · 레벨업 시 증가" 안내 문구). 레벨 박스 아래 새 **"🌟 레벨업!"** 버튼이 경험 태그 등급 합이 새 레벨 임계값을 넘을 때마다(레벨 Ⅰ→Ⅱ→Ⅲ→Ⅳ→Ⅴ 각 구간 통과 시 1회씩, 여러 구간을 한번에 넘으면 그만큼 여러 번) 나타나고, 누르면 체력/정신력/피로도 중 하나를 골라 최대치 +1. 각 캐릭터에 `levelUpsUsed`(이미 사용한 레벨업 횟수) 필드를 신설해 추적 — "레벨업 가능 횟수 = 현재 레벨 임계값 인덱스 − 이미 사용한 횟수"로 계산. 기존 저장 데이터는 이미 손으로 최대치를 올려둔 만큼(`(maxHealth-5)+(maxMind-3)+(maxFatigue-3)`)을 `levelUpsUsed`로 역산해 이중 지급을 방지.
- 침식 태그 정화는 이번 변경과 무관 — 기존처럼 각 침식 태그 옆 "정화" 버튼으로 언제든 가능(레벨업에 종속시키지 않음, "미확인 사항" 1번 항목 그대로 유지).
- **검증**: Playwright로 (1) 태그 이름에 여러 글자를 실제 키 입력처럼 순차 입력해 포커스 유지·최종값 일치 확인, (2) 페이지 전체에 걸쳐 네이티브 `dialog` 이벤트가 단 한 번도 발생하지 않는지 확인(발생하면 테스트 실패 처리), (3) 삭제·초기화·GM PIN 설정/검증·레벨업 선택을 전부 커스텀 모달 버튼 클릭으로 수행해 실제로 동작하는지 확인, (4) "최대 +1" 버튼이 어디에도 없는지 확인. 전부 통과.

### 17차 개정 — 핵심 자원 −/+ 버튼 ReferenceError 수정 (16차 배포 직후 발견)
사용자가 브라우저 콘솔 에러를 그대로 전달: `Uncaught Error: Uncaught ReferenceError: p is not defined` / `Uncaught Error: Uncaught ReferenceError: max is not defined`.

- **원인**: `renderResources()`가 체력/정신력/피로도 각 행의 −/+ 버튼을 생성할 때 `onclick="setRes('${k}',Math.max(0,p[k]-1))"`처럼 **`Math.max(0,p[k]-1)`라는 JS 소스 텍스트를 템플릿 리터럴의 `${}`로 감싸지 않은 채 그대로** HTML 속성 문자열에 심어놨음. 인라인 이벤트 핸들러는 전역 스코프에서 실행되므로, 렌더 함수 안에서만 존재하는 지역 변수 `p`(현재 캐릭터)·`max`(해당 자원의 최대치)를 찾지 못해 클릭 시 `ReferenceError`가 발생 — 15~16차에서 같은 유형의 버그(`editErosion`/`editInventory` 등)를 고칠 때 이 두 버튼은 손대지 않아서 원본 프로토타입 때부터의 버그가 그대로 남아있었고, 이 버튼을 클릭하는 자동 테스트가 그동안 없어서 발견되지 못했음.
- **증상**: 자원 행의 −/+ 버튼을 눌러도 값이 전혀 바뀌지 않고 콘솔에만 에러가 남음(태그 등급 상자 클릭은 `${k}`,`${i+1}`을 이미 올바르게 `${}`로 감싸고 있어서 정상 동작 — 이 두 버튼만의 문제였음).
- **수정**: 계산식 자체를 `${}` 안으로 옮겨 `onclick="setRes('${k}',${Math.max(0,p[k]-1)})"`처럼 **렌더 시점에 계산된 숫자 리터럴만** HTML 속성에 삽입되도록 수정(토큰 상자 `onclick`이 이미 쓰던 것과 동일한 패턴으로 통일).
- **검증**: 신규 Playwright 테스트(`test_app3.py`)로 체력/정신력/피로도 3개 행의 −/+ 버튼을 각각 클릭해 값이 정상 증감·원복되고 `pageerror`(ReferenceError 포함)·네이티브 다이얼로그가 전혀 발생하지 않는지 확인. 기존 16차 회귀 테스트(`test_app2.py`)도 재실행해 이번 수정이 다른 기능에 영향 없음을 재확인 — 전부 통과.

### 18차 개정 — 웹 버전을 PDF 캐릭터 시트("character_sheet.html")의 구성·비주얼 그대로 이식 (앞/뒤 2페이지 구조)
사용자가 실제 PDF 출력물 이미지(앞면/뒷면)를 첨부하며 "웹 사이트 구성을 PDF 캐릭터 시트지 그대로 만들어 줄 수 있어?"라고 요청. `AskUserQuestion`으로 (1) 이식 범위(앞/뒤 2페이지 구조까지 전부 vs 지금 구조 유지+스타일만) (2) 뒷면 초상화 칸 처리(실제 업로드 기능 vs 디자인만) (3) 규칙 요약본 전체 추가 여부를 확인 — 전부 "추천" 옵션(①2페이지 구조까지 전부 ②이미지 업로드 기능 추가 ③10개 항목 전체 추가)으로 확정. 웹 버전이 10차 개정(아이콘 배지 스타일)을 한 번도 반영한 적이 없었다는 것도 이번에 확인됨 — 10차는 PDF·엑셀에만 적용되고 웹은 GPT 프로토타입 당시의 단순한 디자인 그대로 남아있었음.

**1) 구조 전체 이식**: `#playerView`를 캐릭터 관리 툴바(기존 유지) + 스크롤 가능한 "종이 2장"(`.paper.front`/`.paper.back`, 각 210mm 폭, `character_sheet.html`의 mm/pt 단위·클래스 구조를 거의 그대로 재사용)로 재구성.
- **앞면**: 로고(아래 참고) + PC이름/자기소개 + 노치 코너 레벨 배너(육각 클립패스, `roman`/`tagSum`에 기존 로직 그대로 연결 + 그 아래 레벨업 버튼) · 태생 태그 3장(육각 "1" 배지 카드) · 경험 태그(진짜 `<table>`로 전환, 드롭다운은 기존 그대로) · 침식 태그(해골 육각 배지 카드) · 핵심 자원(♥/✦/◐ 육각 배지 + 트래커 박스, 클릭으로 즉시 값 지정 + 보조 −/+ 버튼 유지) · 판정(주사위 굴리기 + 10+/5~9/4- 참고 박스 + 점선 규칙 박스 3종) · 마법 물품(이름/전용 태그는 기존 그대로, "형태"(무기류·방어구류·마법도구류) 라디오 버튼은 PDF엔 있었지만 웹엔 없던 필드라 이번에 신규 추가 — `magicForm` 필드) · 장비 & 소지품(진짜 `<table>` 전환 + 착용무기·방어구·화폐 4종을 한 줄 "gear-foot"으로 통합).
- **뒷면**: 로고 + "백스토리 카드" 제목 + PC이름 미러(읽기 전용, 앞면 입력값과 자동 동기화) · 초상화 박스(아래 참고) + 정보란(가치관/나이/키·몸무게/외모특징×2 — "외모특징" 칸이 기존엔 없었어서 `look1`/`look2` 필드 신규 추가) · 상세 백스토리 · **마스터 비밀 메모 박스**(PDF는 물리적으로 "접는 선"으로 숨기는 개념이지만, 웹은 이미 15차에서 GM 세션 탭 + PIN 잠금이라는 더 안전한 방식으로 분리해뒀으므로 실제 비밀 텍스트는 넣지 않고 "GM 세션 탭에서 PIN으로 보호되어 작성·열람됩니다" 안내만 표시하는 장식용 박스로 처리 — 15차의 보안 결정을 훼손하지 않기 위한 의도적 선택) · **규칙 요약본**(10개 항목, 2단 컬럼, `character_sheet.html`의 문구를 그대로 복사).
- 화면 상단에 "◆ 캐릭터 시트 — 앞면" / "◆ 백스토리 카드 — 뒷면" 라벨을 페이지 밖에 작게 추가(스크롤 중 위치 파악용, 인쇄 시에는 숨김) — PDF에는 없는 웹 전용 내비게이션 보조 요소.
- GM 세션 탭(대시보드)은 이번 변경 대상에서 제외 — 사용자의 요청이 "캐릭터 시트지"(플레이어 시트) 구성에 한정되었고, GM 대시보드는 애초에 종이 문서가 아닌 화면 전용 도구이므로 그대로 유지.

**2) 로고**: 기존에 CSS로 그린 "✦ TAG & DICE" 텍스트 로고 대신, 프로젝트 파일의 실제 로고 이미지(`logo_transparent.png`, 용/주사위 그래픽)를 축소(세로 480px)·팔레트 압축(pngquant)해 약 72KB PNG로 최적화한 뒤 base64로 파일에 직접 내장(외부 파일 참조 없이 단일 HTML 파일 구조 유지). 앞/뒤 페이지 헤더에 동일하게 사용.

**3) 초상화 업로드 기능 (신규)**: 뒷면 초상화 박스를 클릭하면 이미지 파일 선택 → `<canvas>`로 최대 480px로 축소 후 JPEG(품질 0.82)로 재인코딩 → `data:` URL로 캐릭터별 저장(`p.portrait`). 원본 이미지를 그대로 저장하면 localStorage 용량 한도(브라우저마다 다르지만 보통 5~10MB)를 쉽게 넘길 수 있어 업로드 시점에 축소·재압축하도록 설계. "✕ 제거" 버튼으로 삭제 가능. `localStorage.setItem` 실패(용량 초과 등) 시 조용히 실패하지 않도록 `persistQuiet()`에 try/catch + 안내 모달을 추가.

**4) 마법 물품 "형태" 필드 신규 추가**: PDF에는 있었지만 웹 프로토타입에는 원래 없던 필드 — 무기류/방어구류/마법도구류 라디오 버튼(`magicForm`)을 추가해 PDF와 동일한 항목 구성을 갖추도록 보완.

**5) 의도적으로 다르게 처리한 부분**:
- 헤더의 종족/배경/본능 "미니 요약 줄"(PDF `.head .misc`)은 웹에 옮기지 않음 — PDF는 한눈에 보는 요약 줄과 아래 태생 태그 카드가 별개의 빈칸(종이라 둘 다 손으로 적음)이지만, 웹은 데이터가 하나뿐이라 같은 값을 두 군데 보여주면 "어느 쪽이 진짜 입력칸인지" 혼동을 줄 수 있어 태생 태그 카드 쪽 한 곳에만 입력하도록 단순화.
- 소지품 태그 설명문은 PDF의 축약된 한 줄 대신 15차에서 추가한 상세 설명문을 그대로 유지(웹은 지면 제약이 없어 더 친절한 설명이 낫다고 판단).
- 핵심 자원의 −/+ 버튼(16~17차에서 만든 것)은 PDF엔 없지만(종이라 손으로 칸을 채움), 트래커 박스를 직접 클릭해도 동일하게 값을 바로 지정할 수 있어 사실상 중복 기능임에도 불구하고, 기존 사용자가 이미 쓰고 있었을 조작 방식을 임의로 제거하지 않기 위해 작게 축소된 형태로 유지.
- 인쇄(`window.print()`) 시 주사위 굴리기 카드(`.rollcard`)는 숨기고 10+/5~9/4- 참고 박스만 남도록 처리 — 인쇄 결과가 실제 `character_sheet.pdf`와 더 가깝게 보이도록 함.

- 크기/굵기 문제(♥·✦·☠·"1" 등급 숫자 공통): `@media screen` 전용 규칙으로 화면에서만 배지 5.6mm→9mm, 글자 6.2pt→11pt, 굵기 900→700으로 확대. `@media print`는 별개의 미디어 타입이라 이 규칙이 자동으로 제외되어 인쇄 결과물은 기존 PDF와 완전히 동일하게 유지됨.
- 글리프 자체 문제(피로도 아이콘): 반원(◐)을 원형 전체 채움(●, U+25CF)으로 교체. 이건 화면 전용 CSS가 아니라 JS 데이터 자체를 바꾼 것이라 웹 버전의 인쇄 출력에도 동일하게 반영됨(화면·인쇄 모두 ●). **참고**: 이 글리프 문제는 브라우저 폰트 렌더링에서 기인한 것으로 보여, 동일한 mm/pt 브라우저 렌더링 방식을 쓰는 `character_sheet.html`/PDF 원본에도 같은 증상이 있을 가능성이 있음 — 이번 라운드는 "웹 캐릭터 시트" 한정 요청이라 PDF 원본은 손대지 않았고, 확인이 필요한 항목으로 남겨둠(프로젝트 설계노트의 "남은 미확인 사항" 참고).

### 20차 개정 — PC 좌우 배치가 실제 화면 폭에 맞게 자동 축소되도록 수정 (19차 배포 직후 발견)
사용자가 실제 배포된 파일을 Cowork 미리보기로 열어본 스크린샷을 첨부하며 "이렇게 잘려보이게 하지말고 전체적으로 보이게 해줬으면 해"라고 요청.

**원인**: 앞/뒤 페이지(각 210mm)를 좌우로 배치하면 필요한 폭은 `210mm×2 + 16px 간격 ≈ 1603px`인데, `.wrap{max-width:1420px}`(패딩 제외 시 약 1380px 실사용폭)에 막혀 **1800px짜리 넓은 브라우저 창에서도** 뒷면 오른쪽 일부가 어차피 잘렸었음 — 19차 검증 당시 "앞/뒤가 서로 옆에 나란히 있는지"(상대 위치)만 바운딩박스로 확인했지, "그게 실제로 창 안에 다 들어오는지"(절대적으로 잘리지 않는지)는 확인하지 않아서 이 문제를 놓쳤음. 게다가 사용자가 실제로 보고 있던 화면은 Cowork 대화 안의 미리보기 패널이라 그보다도 더 좁았을 가능성이 높음.

**수정**: `.papers-scroll`(두 페이지를 감싸는 컨테이너)이 항상 자기 콘텐츠의 "원래" 폭(1603px 또는 모바일에서는 페이지 1장 폭)만큼 자기 크기를 갖도록(`width:max-content`) 만든 뒤, 새 `fitPapers()` 함수가 그 원래 폭과 실제로 쓸 수 있는 폭(부모 컨테이너의 `clientWidth`)을 비교해서 `transform:scale(...)`로 **한 화면에 다 들어올 때까지 균일하게 축소**(절대 확대는 하지 않음, 최대 1배)하도록 구현. 창 크기가 바뀌거나(리사이즈 이벤트) 시트 내용 구조가 바뀌면(`ResizeObserver`로 감지 — 예: 레벨업 버튼이 나타나 높이가 바뀌는 경우) 자동으로 다시 계산됨. 이 방식 덕분에 기존에 "미확인 사항"으로 남아있던 모바일 가로 스크롤 문제도 부수적으로 해결됨 — 모바일에서도 페이지 1장이 화면 폭에 맞게 축소돼 가로 스크롤 없이 전체가 보임.
- 인쇄(`@media print`)와 이미지 내보내기(`exportImage()`, html2canvas)는 이 화면용 축소와 무관하게 항상 **원래 크기(배율 1)**로 처리되도록 별도 예외 처리 — 인쇄는 CSS로 `transform:none!important`를 강제하고, 이미지 내보내기는 캡처 직전에 잠깐 `transform`을 리셋했다가 캡처 후 원래대로 복원.

**검증**: `test_app4.py`에 실제 버그 재현 조건(1800·1420·1300·1000·480px 등 다양한 폭)에서 앞면·뒷면 페이지의 바운딩박스가 **뷰포트 밖으로 한 픽셀도 벗어나지 않는지**(왼쪽이 0 미만이 아닌지, 오른쪽이 창 폭을 넘지 않는지) 직접 확인하는 항목을 추가 — 이번 문제는 "나란히 배치되어 있는지"만으로는 못 잡는다는 것을 실제로 겪었으므로, 상대 배치 확인과는 별개로 유지. 인쇄 시 `transform`이 `none`으로 리셋되는지도 함께 확인. 리사이즈·클릭·타이핑이 축소된 상태에서도 정상 동작하는지(좌표 변환 문제 없는지) 수동으로도 재확인. 전체 재실행 결과 네이티브 다이얼로그·페이지 에러 0건으로 전부 통과.
- (자체 발견) 이 인쇄-transform 검증 코드에 `page.emulate_media(media="screen")`을 값을 읽기도 전에 먼저 호출해버리는 순서 버그가 있어서, 실제로는 매번 "화면용(축소된)" transform 값을 읽고 있었음 — 마침 그 값이 우연히 `none`이 아니게 되자(폭이 줄며 축소가 걸리자) 비로소 실패해서 드러남. 앱 쪽 CSS(`@media print`의 `transform:none!important`)는 처음부터 올바르게 동작하고 있었던 것으로 재확인했고, 문제는 테스트 코드의 순서뿐이었음. `emulate_media` 값을 읽어야 하는 지점보다 먼저 되돌리지 않도록 순서를 고쳐서 재통과시킴.

### 21차 개정 — 화면 높이까지 고려한 완전 자동 축소로 스크롤바 자체를 제거 (20차 배포 직후 발견)
사용자 피드백: "브라우저 창에 실제로 화면 안에 다 들어와야지 스크롤바가 생기면 안돼. 굳이 있을 필요도 없고. 캐릭터 시트랑 백스토리 카드가 조금 더 가로로 넓어져도 상관없어."

**원인**: 20차 `fitPapers()`는 가로 폭만 기준으로 축소했고 세로 높이는 전혀 고려하지 않음 — `document.documentElement.scrollHeight`/`clientHeight`를 여러 창 크기에서 직접 측정해보니, 1800x1400처럼 아주 넉넉한 경우를 빼면 1420x900·1300x800·1200x700·1600x750·1000x900·1000x600·900x650 등 대부분의 현실적인 창 크기에서 세로 스크롤이 발생하고 있었음(수치로 확인).

**수정**:
1. `fitPapers()`가 `viewport.getBoundingClientRect().top`으로 시트 위쪽(상단바+툴바)이 차지하는 실제 공간을 측정해 `availableHeight = window.innerHeight - top - 20(=.wrap 하단 패딩)`을 구하고, `scale = Math.max(0.15, Math.min(1, 가로비율, 세로비율))`로 가로·세로 중 더 빡빡한 쪽에 맞춰 축소하도록 변경. 0.15는 극단적으로 짧은 창에서 배율이 음수/0에 가까워지는 것만 막는 안전장치이며 "가독성 하한"이 아님 — 명시적으로 주석에 남겨둠.
2. `.wrap{max-width:1420px}` → `max-width:1680px`로 확대(두 페이지 나란히 필요한 실제 폭 ≈1603px보다 여유 있게) — "카드가 넓어져도 상관없다"는 사용자 발언을 "가로 여유가 있으면 굳이 줄이지 않는다"로 반영.
3. `ResizeObserver`가 감시하는 대상에 `.toolbar`를 추가 — 시트 내부 콘텐츠가 아니라 툴바 자체의 높이가 바뀌는 경우(좁은 화면에서 버튼 줄바꿈 등)도 다시 계산되도록 함.

**트레이드오프**: 세로 공간이 부족한 창(예: 1366x768)에서는 20차 때보다 더 작게(약 43%) 줄어듦 — "스크롤바 없음"을 우선한 결과이며, 필요하면 최소 가독 배율 + 약간의 스크롤 허용으로 절충 가능(사용자에게 명시적으로 공유, 미확인 사항으로 기록).

**검증**: `test_app4.py` 17b 항목을 가로 5개 값 → 가로×세로 9개 조합(1800x1400/1680x900/1420x900/1366x768/1300x800/1200x700/1000x600/900x650/480x800)으로 확장하고, 페이지 바운딩박스 클리핑 체크에 더해 `document.documentElement`의 `scrollWidth<=clientWidth+1` 및 `scrollHeight<=clientHeight+1`(=스크롤바 없음)을 직접 단언하는 체크를 추가 — 전부 통과. 별도 스크립트로 가장 작은 배율(~0.169)에서 텍스트 입력·자원 −버튼 클릭이 정상 동작하는지도 확인(정상).

### 22차 개정 — "스크롤바 없음"보다 가독성 우선: 최소 배율 하한 신설 (21차 배포 직후 발견)
사용자 피드백: "화면 비율이랑 폰트가 전체적으로 너무 작아서 보기가 힘들어." `AskUserQuestion`으로 절충 방향을 확인한 결과 **"최소 크기 보장 + 부족하면 스크롤"**로 확정.

**원인**: 21차는 "스크롤바가 절대 생기면 안 된다"를 우선해 가로·세로 모두에 거의 하한 없는(0.15) 축소를 허용했음. 실측해보니 1366×768(흔한 노트북 해상도) 같은 평범한 창에서도 배율이 약 0.4~0.6까지 떨어졌는데, 이 시트는 애초에 A4 인쇄를 기준으로 6~9pt대의 작은 글자를 쓰고 있어(화면 전용 확대 없이) 그 상태에서 다시 축소되면 실제로 읽기 어려운 수준이 됨.

**수정**: `fitPapers()`에 `MIN_COMFORTABLE_SCALE=0.85` 하한을 추가하되, 모드에 따라 다르게 적용.
- **데스크톱/태블릿(앞뒤 페이지 좌우 2단 배치 모드)**: 배율이 0.85 밑으로는 내려가지 않도록 하한을 걸고, 그 결과 화면에 다 안 들어가면(가로든 세로든) 스크롤로 나머지를 보게 함 — "스크롤 없음"보다 "읽을 수 있는 크기"를 우선.
- **모바일(좁은 화면에서 세로로 쌓이는 1페이지 모드, 950px 이하)**: 하한을 적용하지 않고 기존처럼 **가로 폭을 항상 100% 우선 준수** — 이미 좁은 폰 화면에 가로 스크롤까지 생기는 건 세로 스크롤보다 더 나쁜 경험이라고 판단, 20차의 "모바일 가로 스크롤 없음" 보장은 그대로 유지.
- 현재 어느 모드인지는 `.papers-scroll`의 계산된 `flex-direction`(CSS 950px 미디어 쿼리와 연동)으로 판별해 950이라는 숫자를 JS에 중복 하드코딩하지 않도록 함.

**트레이드오프**: 데스크톱에서도 창이 충분히 넓지 않으면(예: 1000px 폭) 이제 뒷면 카드 오른쪽 일부를 보려면 가로로 살짝 스크롤해야 할 수 있음 — 이는 20차 이전의 "잘려서 아예 못 보던" 상태와는 달리 스크롤로 언제든 전부 볼 수 있는 상태이지만, 화면만 보면 비슷하게 느껴질 수 있어 사용자에게 명확히 설명 필요. 실제로 1366×768·1000×700에서 스크린샷을 찍어 직접 육안으로 확인 — 1366×768은 앞/뒤 모두 스크롤 없이 읽기 편한 크기로 표시되고, 1000×700은 앞면은 완전히 보이되 뒷면 오른쪽 일부가 화면 밖으로 나가 가로 스크롤이 필요한 상태임을 확인함.

**검증**: `test_app4.py` 17b 항목을 3그룹으로 재구성 — (a) 여유로운 창(1800×1400)에서는 여전히 스크롤바가 전혀 없어야 함, (b) 데스크톱 폭이지만 빡빡한 창들(1680×900~1000×600)에서는 배율이 정확히 0.85(오차 0.01 이내)로 고정되는지, (c) 모바일 폭(900×650, 480×800)에서는 항상 스택 모드로 전환되고 가로 방향은 여전히 전혀 잘리지 않는지. 전부 통과. 추가로 실제 스크린샷 2장을 육안으로 검토해 텍스트가 실제로 읽기 편해졌는지 확인.

### 23차 개정 — 창에 여유가 있으면 최대 175%까지 확대 (가로 폭 기준, 세로 스크롤 허용) (22차 배포 직후 발견)
사용자 피드백: Cowork 미리보기 스크린샷(일반/최대화 상태)과 함께 "여기서, +75% 정도 더 크게 확대되서 보이게 할 수 없을까".

**원인**: 이번 건은 원인이 세 겹이었음.
1. 22차까지는 배율 상한이 사실상 1(원본 크기)로 고정 — 20차에서 정한 "절대 확대는 하지 않는다" 원칙 때문에, 창이 아무리 넓어도 원본보다 크게 보여준 적이 없었음.
2. 상한만 올리는 것으로는 부족했음: `scroll.style.transform = scale<0.999 ? scale(...) : "none"` 분기가 "배율 0.999 이상이면 변형 없음(=원본 그대로)"이라는, 배율이 1을 넘을 수 없던 시절의 가정을 그대로 갖고 있어서, 배율이 예컨대 1.3으로 계산되어도 실제로는 transform이 적용되지 않고 조용히 원본 크기로 렌더링되는 버그가 있었음(코드 작성 중 자체 발견, 배포 전에 수정).
3. `.wrap{max-width:1680px}`도 병목 — 2단 배치 시 필요한 실제 폭(~1603px) 기준 175%는 약 2845px인데 컨테이너 자체가 1680px로 막혀 있어 상한을 아무리 올려도 물리적으로 도달 불가능했음.
4. 위 세 가지를 전부 고친 뒤에도, 사용자가 첨부한 스크린샷과 동일한 2560×1400 해상도로 직접 측정하니 배율이 0.868배 → 0.868배로 전혀 변하지 않았음. 원인은 이 시트의 세로 자연 높이(~1442px)가 웬만한 모니터의 실사용 가능 높이(헤더·툴바를 제외하면 보통 1200~1300px대)보다 항상 더 크다는 것 — "가로·세로 중 더 빡빡한 쪽에 맞추기" 방식에서는 세로가 항상 병목이 되어, 가로로 아무리 여유가 있어도 전혀 활용되지 못하는 구조였음.

**수정**:
1. `MAX_SCALE=1.75` 상수를 추가하고 배율 계산의 상한을 1 → 1.75로 확장.
2. `scroll.style.transform` 결정 로직을 `scale<0.999 ? ... : "none"`에서 `Math.abs(scale-1)<0.001 ? "none" : scale(...)`로 수정 — 1보다 작을 때뿐 아니라 1보다 클 때도 정상적으로 변형이 적용되도록 함.
3. `.wrap{max-width:1680px}` → `2900px`로 확대.
4. **(핵심) 데스크톱/2단 모드의 배율 계산 방식 자체를 변경**: "가로·세로 중 더 빡빡한 쪽에 맞추기"에서 **"가로 폭 기준으로만 계산하고, 그 결과 세로가 넘치면 스크롤 허용"**으로 바꿈. 세 가지만 고치고 끝냈다면 실제 모니터에서는 체감 변화가 거의 없었을 것이므로, `AskUserQuestion`으로 트레이드오프를 직접 확인(옵션: 가로 기준 최대 확대·절충안·현행 유지 3가지 제시) → **"가로 기준 최대 확대, 세로 스크롤 감수"**로 확정. 모바일(스택 모드)은 원래부터 가로가 항상 상한이라 변경 없음.

**트레이드오프**: 데스크톱 모드에서는 이제 창이 넓기만 하면(높이와 무관하게) 배율이 커지고, 그만큼 시트 전체를 보려면 세로 스크롤이 필요해짐 — 21~22차가 줄여온 "세로 스크롤"이 다시 늘어나는 방향의 변경으로, "스크롤 없음"보다 "크고 읽기 편한 시트"를 우선한다는 트레이드오프를 사용자가 직접 선택한 것임. 예: 사용자의 2560×1400 화면에서는 배율이 0.868배 → 1.572배(약 +81%, 요청한 "+75%"에 근접)로 커지지만, 시트 전체를 보려면 세로로 화면 높이의 약 1.7배 분량을 스크롤해야 함. 가로 스크롤은 이전과 동일하게 어떤 경우에도 발생하지 않음(배율이 가로 기준으로 계산되므로 구조적으로 가로 초과가 불가능).

**검증**: `test_app4.py` 17b 항목을 전면 재작성.
- (a) 1800×1400: 배율이 가로 기준(~1.098)으로 올라가고, 세로 스크롤이 실제로 발생하되 가로 스크롤은 없음을 확인.
- (b) 1680×900~1000×600(6개 창 크기): 가로 기준 배율이 0.85 하한보다 큰 구간(1680→약 1.02, 1420→약 0.86)과 하한에 걸리는 구간(1366 이하→0.85 고정)을 실측값과 대조, 항상 가로 무손실인지 확인.
- (c) 900×650, 480×800(모바일 폭): 기존과 동일하게 스택 모드 + 가로 무손실 유지 확인(회귀 없음).
- (d) 신규: 2200×1200(부분 확대, 상한 미도달)과 3200×2900(상한 1.75 고정)에서 배율과 가로 무손실 확인. 3200×2900(배율 1.75) 상태에서 이름 입력창에 실제로 클릭+타이핑하고 2d6 굴리기 버튼을 클릭해 정상 반영되는지까지 확인 — 확대된 상태에서도 클릭/포커스 위치 계산(hit-testing)이 정상 동작함을 실증.
- 전체 스위트 5회 연속 재실행으로 큰 뷰포트 전환 시 타이밍 이슈(최초 1회 확대 상한 미도달로 실패한 사례 발견 → 대기시간을 150ms에서 300ms로 늘려 해결)가 재발하지 않음을 확인.
- 추가로 사용자의 실제 스크린샷과 동일한 2560×1400 해상도로 스크린샷을 찍어 육안으로 검토, 실제로 시트가 훨씬 크게 보이는 것을 확인.

### 24차 개정 — "확대는 유지, 세로 스크롤 감수" → "세로 스크롤 완전 제거"로 재변경 (23차 배포 직후 발견)
사용자가 23차 결과물을 실제로 열어본 화면 스크린샷(스크롤바가 보이는 상태)을 첨부하며 "화면 비율은 좋은데 왜 굳이 필요없는 스크롤바가 추가되는지 모르겠어"라고 질문.

**원인**: 버그가 아니라 23차에서 사용자가 직접 선택한 "가로 기준 최대 확대, 세로 스크롤 감수"의 정확한 수학적 결과였음. 실제로 재현해보니(사용자 스크린샷과 동일한 2624×1400) 배율 1.612배, 세로 초과분 1073px(화면 높이의 75%)이 정확히 발생하고 있었음 — 계산상 이 창 높이에서 세로 스크롤을 완전히 없애려면 배율이 0.868배(오히려 원본보다 작음)여야 하므로, "지금 크기 그대로 스크롤만 없앤다"는 애초에 성립할 수 없는 조합이었음. 크기와 스크롤량이 정확히 같이 움직이는 값이라는 걸 `AskUserQuestion`으로 구체적인 수치(0.87배/스크롤 0% ~ 1.75배/스크롤 75%)와 함께 다시 확인.

**수정**: 4가지 선택지(확대 유지+스크롤 최소화 절충안 / 스크롤 완전 제거 / 원본 100% 고정 / 현재(23차) 그대로 유지) 중 **"스크롤 완전히 제거"**를 선택함에 따라, 데스크톱/2단 모드의 배율 공식을 23차의 "가로 폭 기준"에서 다시 **`min(가로 배율, 세로 배율)`**(21~22차와 동일한, 스크롤 자체가 생기지 않는 방식)로 되돌림. 다만 23차에서 올린 `MAX_SCALE=1.75` 상한과 `scale>=1`일 때도 transform이 정상 적용되도록 한 버그 수정은 그대로 유지 — 창이 가로·세로 양쪽 모두 실제로 넉넉할 때(예: 매우 크고 세로로도 긴 모니터)는 여전히 원본보다 확대될 수 있고, 이번에 되돌린 것은 "세로 공간이 부족한데도 가로만 보고 억지로 키우는" 부분뿐임.

**트레이드오프(사용자에게 명확히 전달)**: 사용자의 실제 창처럼 "가로는 넓지만 세로는 넉넉하지 않은" 형태의 모니터에서는, 이번 되돌림으로 인해 **23차 이전(22차)과 사실상 동일한 크기(약 0.87배)로 돌아감** — 즉 이번 라운드로 시작된 "+75% 확대" 요청은 이런 화면 비율에서는 시각적으로 거의 원점으로 돌아간 셈. 대신 가로로 넓은 공간을 시트가 실제로 채우지는 못하고 다시 여백으로 남게 됨(23차 이전과 동일한 모습). 세로로도 충분히 큰 창(예: 세로로 길게 늘인 창, 초고해상도 모니터)에서는 여전히 확대 효과를 볼 수 있음.

**검증**: `test_app4.py` 17b 항목을 다시 22차 방식(그룹 a/b/c: 여유 창은 완전 무스크롤, 데스크톱 빡빡한 창은 배율 정확히 0.85, 모바일은 가로 무손실)으로 되돌리고, 그룹 d는 "가로·세로 모두 진짜 넉넉한 창"(3200×1800 부분 확대, 3200×2900 상한 1.75 고정)에서 **양방향 모두** 스크롤바가 없는지 확인하도록 재구성(23차 때는 세로 스크롤을 허용했었으므로 가로만 확인했었음) + 확대 상태에서의 클릭/타이핑 상호작용 확인은 유지. 3회 연속 재실행 통과. 추가로 사용자의 실제 스크린샷과 동일한 2624×1400에서 스크린샷을 찍어 배율이 정확히 0.868배로 돌아오고 스크롤바가 사라졌음을 육안으로 확인.

### 25차 개정 — 축소된 시트가 한쪽으로 쏠리는 "빈 공간" 문제 수정 (24차 배포 직후 발견)
사용자가 24차 결과물을 다른 도구로 손보려 시도한 흔적이 담긴 스크린샷(별도 브라우저 탭에서 일반적인 CSS 조언을 참고해 수정을 시도)을 첨부하며 "이 비율이랑 빈공간 문제를 어떻게 해결하면 좋을까. 수정하면 할 수록 처음보다 더 이상해지는거 같아"라고 질문.

**원인**: 20~24차에서 다뤄온 "배율(크기)" 문제와는 별개로, 지금까지 손대지 않았던 문제였음. 시트를 담는 컨테이너(`.papers-viewport`)는 폭이 넉넉한 `.wrap`(최대 2900px) 안에서 항상 왼쪽 끝에 붙어 있었고, 축소된 콘텐츠보다 컨테이너가 넓게 남을 때 그 여백을 중앙으로 분배하는 규칙이 없었음. 특히 24차 공식에서는 "세로 공간이 부족해 배율이 가로 기준보다 작게 잡히는" 경우가 흔한데, 이때 축소된 시트 두 장이 왼쪽에 붙고 남는 폭 전부가 오른쪽 한쪽에만 쌓였음 — 정확히 스크린샷에서 지적된 그 여백.

**참고**: 사용자가 함께 전달한 CSS 수정 제안(`.wrap`을 1400px로 축소, 존재하지 않는 `.sheet`/`.grid-main` 클래스 수정 등)은 실제 코드와 값·클래스명이 맞지 않아 적용하지 않았고, 그대로 적용했다면 20차에서 고쳤던 2단 모드 가로 잘림 버그가 재발할 뻔했음(2단 모드 최소 요구 폭 ≈1603px > 1400px). 이 사실을 먼저 사용자에게 설명한 뒤, 진짜 원인인 "정렬" 문제를 별도로 진단.

**중요**: 23~24차의 "확대냐 세로 스크롤 제거냐"는 사용자가 직접 골라야 하는 트레이드오프였지만, 이번 "빈 공간" 문제는 손해 볼 선택지가 없는 순수한 정렬 버그라서 이번엔 다시 여쭤보지 않고 바로 수정함.

**수정**: (1) `.papers-viewport`에 `margin:0 auto`를 추가해 컨테이너가 `.wrap` 안에서 중앙 정렬되도록 하고, (2) `fitPapers()`가 배율을 계산할 때마다 축소된 콘텐츠의 실제 폭을 `viewport.style.width`에도 반영하도록 해 `margin:auto`가 실제로 작동할 폭 차이(컨테이너 폭 < `.wrap` 폭)를 만들어줌.

**부작용과 재수정**: 폭을 명시적으로 고정하는 방식이 새 버그를 만들었음 — 넓은 창에서 한 번 계산된 뒤 좁은 창으로 줄이면, 직전에 고정해둔 폭이 저절로 줄지 않아 다음 계산의 "사용 가능한 폭" 측정값이 실제보다 부풀려진 채 읽히는 자기참조 오류가 발생. 이 상태로 좁은 창(480×800)에서 시트가 오히려 가로로 넘치는 회귀가 테스트에서 발견됨. `fitPapers()` 맨 앞에서 매 계산 시작 시 `viewport.style.width`를 먼저 초기화한 뒤 측정하도록 수정해 해결.

**검증**: `test_app4.py`에 새 테스트 블록 (e) 추가 — 가로는 넓지만 세로가 부족해 배율이 가로 기준보다 작게 잡히는 창(2400×1000)에서 ① 실제로 배율이 1보다 작은지 ② 좌우 여백이 5px 이상 존재하면서 서로 3px 이내로 동일한지(중앙 정렬 확인) ③ 좁은 창(480×800)을 거쳤다가 같은 크기(2400×1000)로 돌아와도 배율·폭이 그대로인지(자기참조 버그 재발 방지)를 확인. 전체 스위트 8회 연속 재실행(1차 수정 직후 5회 + 회귀 테스트 추가 후 3회) 통과, 매번 네이티브 다이얼로그·페이지 에러 0건. 2400×1000 스크린샷에서 좌우 여백이 각각 518.5px/518.6px로 사실상 동일함을 육안으로도 확인(수정 전 상태를 재현한 비교 스크린샷에서는 좌측 20px·우측 1017px로 한쪽에 쏠려 있었음).

### 26차 개정 — 화면 레이아웃 전면 재설계: "종이를 축소해서 보여주기"를 버리고 진짜 반응형 웹으로 (25차 배포 직후, 사용자 요청)
사용자가 "컨텍스트에 올린 인덱스 파일로 다시 처음부터 만들어야겠는데"라고 요청. 먼저 확인해보니 프로젝트 문서의 `index.html`은 사용자가 처음 올렸던 GPT 원본 프로토타입이 아니라 매 라운드 덮어써 온 최신(25차) 버전이었고(원본은 세션 기록에서 복구 가능함을 확인), 그 사실과 함께 근본 원인을 설명한 뒤 `AskUserQuestion`으로 방향을 확인 → **"웹 전용으로 새로 설계"** + **"인쇄/PDF 저장은 계속 필요"**로 확정.

**근본 원인(20~25차가 여섯 번 반복된 이유)**: 이 시트는 A4 인쇄용 종이(210mm 고정 폭, mm·pt 단위)를 화면에서 `transform:scale()`로 통째로 축소해 보여주는 구조였음. 이 방식에서는 **크기·스크롤·여백이 전부 배율이라는 단 하나의 숫자에 묶여** 있어서, 하나를 고치면 반드시 다른 하나가 틀어짐. 20차(가로 맞춤) → 21차(세로까지, 너무 작아짐) → 22차(최소 배율 하한) → 23차(1.75배 확대, 세로 스크롤 발생) → 24차(스크롤 제거, 크기 원위치) → 25차(여백 쏠림)가 전부 같은 구조적 제약에서 파생된 증상이었음. 인쇄용 종이와 화면용 페이지는 애초에 서로 다른 기하 구조를 원하므로, 하나의 기하 구조를 공유하는 한 이 반복은 끝나지 않음.

**수정 — 화면과 인쇄에 각자의 기하 구조를 부여**:
1. **인쇄는 그대로 둠**: 기존 mm·pt 기반 규칙 전체를 손대지 않고 유지 → "인쇄 / PDF 저장" 결과물은 이전과 완전히 동일.
2. **화면은 새로 작성**: 동일한 DOM에 `@media screen` 블록으로 완전히 새로운 유동형 레이아웃을 부여. 210mm 고정 폭 → 유동 폭, mm·pt 치수 → px 기반 웹 치수(본문 14px, 제목 16px 등 실제로 읽히는 크기), 두 페이지 배치는 `repeat(auto-fit,minmax(min(100%,560px),1fr))` 그리드로 전환 — 공간이 있으면 좌우 2단, 없으면 자동으로 세로 1단이 되며 **중단점(breakpoint)도 JS도 필요 없음**.
3. **`fitPapers()` 및 전체 축소·확대 로직 완전 삭제**(약 6,600자): `transform:scale`, `ResizeObserver`, `MIN_COMFORTABLE_SCALE`/`MAX_SCALE`, viewport 폭·높이 고정 등 20~25차에 걸쳐 쌓인 기계장치를 전부 제거. 이제 레이아웃에 관여하는 JS는 한 줄도 없음.
4. 부수적으로 함께 정리한 것: 인쇄 시에도 적용되던 `@media(max-width:950px)` 블록을 `@media screen and (...)`으로 한정(A4 페이지 폭 794px는 950px 미만이라 실제 프린터에서는 본문이 1단으로 무너질 수 있었음), 인라인 mm 여백·퍼센트 열 너비를 클래스로 이관, 뒷면의 남는 높이를 백스토리 입력칸이 흡수하도록 처리, `exportImage()`에서 불필요해진 transform 저장·복원 제거.

**발견하고 고친 문제 2건**: (a) 인라인 스타일을 클래스로 옮기자 `h2.sec`(0,1,1)가 `.sec-gap`(0,1,0)를 이겨 인쇄 여백 3.4mm가 조용히 사라짐 — `h2.sec.sec-gap`으로 특이성을 맞춰 해결(인쇄 기준선 대조로 발견). (b) 경험 태그 "유형" 열이 인라인 16% 폭 탓에 실제 화면 글꼴에서 54px로 좁아져 드롭다운이 "ㅈ ∨"로 잘림 — 화면에서는 고정 px 폭으로 전환.

**트레이드오프(명확히 전달)**: 이제 시트가 읽을 수 있는 크기로 렌더되므로 **세로 스크롤은 정상적으로 발생**함(1600px 폭 기준 페이지 높이 약 2,175px). 24차에서 "세로 스크롤 완전 제거"를 선택했던 것과는 방향이 다르지만, 그때의 스크롤은 "고정 크기 그림이 창을 넘치는" 스크롤이었고 지금은 일반적인 웹 페이지의 스크롤임 — 대신 글자가 창 크기에 따라 작아지는 일이 완전히 사라짐. 가로 스크롤은 어떤 크기에서도 발생하지 않음.

**검증**:
- **인쇄 동일성**: 재설계 전 인쇄 미디어 기준선(치수 18종 + 전체 스크린샷)을 저장해두고 재설계 후 대조 — 앞/뒤 페이지 크기, 본문 그리드 열 너비, 규칙 요약본 단 수 등 **전 항목 완전 일치**. 픽셀 비교에서 남은 차이는 0.5px 오프셋에 따른 안티앨리어싱뿐이며(구버전은 JS가 남긴 인라인 폭 때문에 인쇄 시 좌표가 창 크기에 따라 달라졌음, 신버전은 항상 x=0으로 결정적), 두 이미지를 육안 대조해 동일함을 확인.
- **테스트**: `test_app4.py`의 17b 항목을 배율 기반에서 반응형 계약 기반으로 전면 재작성 — 12가지 화면 크기(2560×1400 ~ 360×740)에서 ① 가로 넘침 0 ② 두 페이지 모두 화면 밖으로 안 나감 ③ transform 미적용 ④ 1280px 이상 2단 / 1024px 이하 1단 ⑤ 좌우 여백 3px 이내 동일(중앙 정렬) ⑥ **글꼴 크기가 화면 크기와 무관하게 항상 동일**(14px/16px — 축소가 사라졌다는 직접 증거)을 확인. 넓은 창·좁은 창 양쪽에서 타이핑·주사위 클릭이 정상 반영되는지도 확인. 추가로 인쇄 A4 기하 구조(210mm 페이지, 본문 2단, 요약본 2단)를 실측값으로 고정하는 가드를 신설해, 앞으로 화면 쪽 수정이 인쇄를 건드리면 즉시 실패하도록 함. 3회 연속 전체 통과, 네이티브 다이얼로그·페이지 에러 0건.
