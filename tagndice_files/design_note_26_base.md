# 태그 앤 다이스 — 캐릭터 시트 설계 노트 (2026-08-10, 26차 개정)

## 배경
"테스트 기획 시트"(구글 스프레드시트)와 공식 사이트(sites.google.com/view/tag-n-dice)의 규칙 페이지를 조사한 결과, **두 규칙 시스템이 서로 다름**을 확인. 사이트의 태그 기반 서사 시스템(능력치 없음, 체력·정신력·피로도 자원 + 2d6 판정)을 기준으로 채택하고, 기획 시트의 구버전 7능력치 시스템은 미채택.

**중요**: 이후 세션에서 사용자가 여러 차례에 걸쳐 사이트/기획 시트보다도 최신인 규칙을 직접 전달해 옴. **가장 신뢰할 수 있는 규칙 소스는 사용자의 직접 지시**이며, 이 문서의 "수정 이력"이 최신 규칙의 실질적 원천임.

## 수정 이력

### 2차 개정 — 구시대 규칙 삭제
부상 태그(3단계), 개연성(성장 재화), 전투 포지션(전열/후열), 인연(PC간 공유 태그) 전부 제거.

### 3차 개정 — 판정 수치·하중·화폐 규칙 변경
1. 판정 등급: 10+/7~9/6- → **10+/5~9/4-**. 사경 판정도 "2d6 동일 표"이므로 임계값 함께 갱신.
2. 한계 하중 개념 삭제.
3. 화폐: 단일 "조각" → 동화/은화/금화(일상) + 조각(몬스터·마법 전용) 2단계. 환율 1금=10은=100동.

### 4차 개정 — 상세 백스토리 칸 자유 서술화
PDF 뒷면 괘선(줄노트 스타일) 제거 → 빈 여백.

### 5차 개정 — 체력 시작치·침식 태그 한계/정화
1. 체력 시작치 3→**5칸**.
2. 침식 태그 최대 3개, 3개 보유 중 재판정 시 즉사.
3. 레벨업 시 침식 태그 1개 정화 가능.

### 6차 개정 — "휴식" → "야영", "치료" 규칙 신설
치트시트의 "휴식"을 "야영"(보급품/식량 1회분 소비 → 짧은/긴 휴식 선택)으로 교체, "치료" 항목 신규 추가. 이 시점에는 "치료"의 "상처"가 불명확해 "체력 손실"로 잠정 해석.

### 7차 개정 — "체력/상처 칸/컨디션" 규칙 확정
사용자가 상처 칸(피해 시 체력 칸에 표시, 페널티 없음, 가득 차면 즉시 행동불능)과 컨디션(정신력=지적 행동/피로도=신체적 행동, 태그 종류가 아니라 마스터가 행동 묘사로 판단) 규칙을 확정 답변 — 6차 개정의 "상처=체력 손실" 해석이 정확했음을 확인. 정신력/피로도 라벨을 "지식/기능 태그 소모"에서 "지적/신체적 행동에 사용"으로 수정, "자원"을 "컨디션"으로 용어 통일, 치트시트에 컨디션·상처 항목 추가(8→10줄).

### 8차 개정 — PDF 앞면에 컨디션·상처 설명 박스 추가
사용자 피드백: "태그 선언 설명 칸을 넣은 것처럼 상처, 컨디션 설명칸도 넣어야 하지 않아? 마침 빈 공간도 있는데." PDF 앞면 우측 컬럼(핵심자원/판정 아래)에 기존 "태그 선언" 점선 박스(`.ruleref`)와 같은 스타일로 "컨디션"·"상처" 설명 박스 2개를 추가.

### 9차 개정 — "마법 물품" 섹션 신설
사용자 피드백: "모든 파일에 마법 물품에 대한 칸이 없어... 이름을 정하는 칸도 없고." 형태(무기류/방어구류/마법도구류) 선택 + 물품 이름 + 전용 태그(경험 태그와 유일하게 중첩 가능, 세션당 3회·차례당 1회) 규칙을 PDF·엑셀 양쪽에 신설. PDF 오버플로우 발견 → 장비&소지품 표 10→7→5행 축소로 해결(엑셀은 9행 유지, 이때는 PDF/엑셀 행수 불일치 존재 — 11차에서 해소).

### 10차 개정 — 아이콘 배지 스타일 도입 (참고 이미지 기반)
사용자가 흑백 라인아트풍 "던전 배시" 스타일 캐릭터 시트 이미지를 레퍼런스로 제시. `AskUserQuestion`으로 확인 후 **"앞면만 압축"** + **"현재 톤 유지(구조만 차용)"**로 결정. 레벨=노치 코너 배너, 태생 태그=육각 등급 배지("1"), 핵심 자원(체력♥/정신력✦/피로도◐)=육각 아이콘 배지, 침식 태그=해골☠ 배지 카드형 박스로 재구성. 신규 일러스트 없이 순수 CSS(`clip-path`)+유니코드 글리프로만 구현. 엑셀은 미적용(스프레드시트 구조상 부적합 판단). **이때는 PDF·엑셀에만 적용되고 웹 버전은 대상이 아니었음 — 18차에서 웹에도 반영됨.**

### 11차 개정 — "소지품 태그" 시스템 신설 + 뒷면 초상화·백스토리 병합
사용자 피드백 1: "짐칸이 너무 적어" + 소지품 태그 규칙 전문 제공(경험 태그와 별개 슬롯, 최대 10개, 착용 장비·마법 물품·사소한 소지품 제외, 자리가 다 차면 기존 태그를 버리고 즉시 교체 가능).
1. 기존 "장비 & 소지품" 3열 표(PDF 5행/엑셀 9행, 불일치)를 폐지 — **양쪽 모두 "#"+"소지품 태그" 2열 × 10행 표로 통일**.
2. "착용 무기"·"착용 방어구" 필드 신설(소지품 한도 제외 명시). PDF는 화폐 필드와 한 줄(6칸)로 통합.
3. **PDF 오버플로우 재발**(9차와 동일 유형) → 핵심자원 행간격·설명박스 패딩·침식카드 높이·마법물품 패딩·소지품표 셀패딩 전반 축소로 약 25mm 확보, 재검증 완료.
4. 엑셀은 동일 구조("착용 장비 & 소지품 태그" 섹션) 반영.

사용자 피드백 2: "뒷면 백스토리 카드 공백이 신경쓰임. 초상화 부분이랑 백스[토리] 부분을 합쳐줄 순 없을까?" → 뒷면 3열 그리드(초상화+기본정보 47mm | 백스토리 1fr | GM메모 30mm)를 **2열 그리드(통합 패널 1fr | GM메모 30mm)로 재구성**. 통합 패널 내부: 상단에 초상화(정사각)+기본정보 가로 배치 → 구분선 → 그 아래 상세 백스토리가 남은 높이 전부 차지.

### 12차 개정 — 초상화 박스 확대
사용자 피드백: "PDF 파일 초상화 칸이 너무 작은거 같아." `.portrait.sp` 폭을 **40mm → 60mm**로 확대. 엑셀은 초상화 개념 자체가 없어 해당 없음.

### 13차 개정 — "규칙 치트시트" → "규칙 요약본" 개명, 세션 기록 삭제, 2단 컬럼화
사용자 피드백: "규칙 치트 시트는 규칙 요약본으로 이름 수정해주고. 세션 기록 표는 지워줘, 그리고 빈 공간을 전부 요약본에 가독성 좋게 정리해줘."
1. PDF: 제목 개명 + 우측 "세션 기록" 표(6행) 삭제 + `.cheat ul`에 `column-count:2`(+`break-inside:avoid`) 적용해 10개 항목이 전체 폭을 2단으로 채우도록 재구성.
2. 엑셀: 동일 개명 + "세션 기록" 섹션(12행) 삭제 + 10개 항목을 좌(1~4열)/우(5~8열) 2단 배치(10행→5행 압축).
3. **세션 기록 기능 자체가 완전히 삭제됨** — "미확인 사항"에 기록.

### 14차 개정 — 레벨 표시 라벨 "장점 태그 등급 합" → "경험 태그 등급 합" (표시만, 계산식은 유지했었음)
사용자 피드백: "PDF랑 파일들 보니까 레벨에 장점 태그 등급 합이라고 적혀있더라. 경험 태그라고 고쳐줘."
- **판단(당시)**: 사용자의 지시는 "적혀있는 텍스트"를 고쳐달라는 표현이라 **표시 라벨만 교체**하고, 실제 계산식(태생 3개 고정 +3 + 경험 태그 등급 합)은 그대로 유지 — 레벨 산정 규칙 자체를 바꾼 것은 아니라고 판단.
- PDF·엑셀 라벨/코멘트 텍스트만 교체. **이 판단은 15차 개정에서 뒤집힘 — 아래 참고.**

### 15차 개정 — 레벨 계산식 자체 수정(+3 제거) + 웹 버전(index.html) 룰 동기화·기능 3종 추가·버그 2건 수정
사용자가 GPT로 만든 별도 웹 프로토타입(`index.html`, 프로젝트 문서로 이미 보관되어 있던 파일)을 공유하며 "여기서 더 세부적으로 기능 추가하거나 업데이트를 하고 싶어"라고 요청. `AskUserQuestion`으로 (1) 레벨 계산식 불일치를 어느 쪽으로 확정할지 (2) 이번 라운드 우선순위 (3) 추가 기능 후보를 확인 후 진행.

**1) 레벨 계산식 정정 (14차의 미확인 사항이 실제로 확정됨)**
- 웹 프로토타입 코드를 열어보니 레벨 계산이 PDF·엑셀과 달랐음 — 프로토타입은 태생 태그 고정 +3 없이 **경험 태그 등급 합만**으로 레벨을 계산하고 있었음(임계값 Ⅰ1~5·Ⅱ6~10·Ⅲ11~15·Ⅳ16~20·Ⅴ21+는 동일).
- `AskUserQuestion`으로 확인한 결과, **"경험 태그 합만"이 실제 의도한 규칙으로 확정**됨. 근거: +3을 포함하면 시작 캐릭터(경험 태그 3P 배분)가 곧바로 레벨 Ⅱ(3+3=6)로 시작하게 되어 "시작은 레벨 Ⅰ"이라는 통상적 기대와 어긋나지만, +3을 빼면 시작 캐릭터는 자연스럽게 레벨 Ⅰ(경험 합 3)로 시작함.
- **엑셀**: 등급 합 수식을 `=SUM(경험태그 등급열)+3` → `=SUM(경험태그 등급열)`로 수정(재계산 0 errors 확인). 코멘트 텍스트도 "태생 3개를 +3으로 더하고..." → "경험 태그 등급 합계이며 태생 태그는 포함되지 않는다"로 수정. "태생 태그 — ... 영구 1등급 장점 태그..." 섹션 헤더도 "고정 1등급, 상시 적용 · 레벨 합산에는 미포함"으로 재정의(태생 태그가 더 이상 "장점 태그"=레벨에 반영되는 태그가 아니게 되었으므로).
- **PDF**: 원래부터 "경험 태그 등급 합" 칸이 수식 없이 손으로 적는 빈칸이라 +3을 언급하는 텍스트가 없었음 — 변경 불필요(14차 라벨 변경만으로 이미 결과적으로 정확했음).
- **웹 프로토타입**: 계산 로직 자체는 원래부터 정답이었으므로 변경 없음. 라벨만 "장점 태그 등급 합" → "경험 태그 등급 합"으로 통일(14차와 동일한 이유).

**2) 웹 버전 룰 동기화**
- "장비 & 소지품" 패널에 착용 장비·마법 물품 제외 캡션 + 11차에서 받은 소지품 규칙 설명문을 추가.
- 화폐를 단일 텍스트 필드 → 금화/은화/동화/조각 4개 필드로 분리(PDF·엑셀과 구조 통일).

**3) 신규 기능 3종 (사용자가 AskUserQuestion에서 선택)**
- **GM 전용 정보 보호**: "GM 전용·마스터 비밀" 메모를 플레이어 시트에서 완전히 제거하고 GM 세션 대시보드로 이동(선택된 캐릭터 기준 표시) + GM 세션 탭에 PIN 잠금 신설.
- **여러 캐릭터 슬롯 관리**: 플레이어 시트 화면에도 캐릭터 선택 드롭다운 + "새 캐릭터" 버튼 신설.
- **인쇄·이미지 내보내기**: "인쇄 / PDF 저장"(`window.print()` + `@media print`) + "이미지 저장"(html2canvas).

**4) 검증 중 발견 및 수정한 기존 버그 2건**: 캐릭터 전환 시 데이터가 섞이는 버그(`save()`가 활성 캐릭터 전환 "후"에 옛 화면 값을 새 캐릭터에 덮어쓰던 구조적 문제 — `persist()`/`save()` 분리로 수정), 침식·소지품 태그 입력이 화면엔 보여도 실제로는 저장되지 않던 버그(인라인 핸들러가 렌더 함수의 지역 변수를 참조해 `ReferenceError`로 조용히 실패 — 전역 함수로 교체).

**5) 검증**: Playwright로 레벨 계산·캐릭터 전환·GM 잠금·침식/소지품 입력·인쇄 스타일을 확인. 이미지 내보내기는 샌드박스 환경의 외부 CDN 차단으로 실제 다운로드까지는 미검증.

### 16차 개정 — 삭제 버튼 미작동 + 태그 타이핑 끊김 수정, 캐릭터 초기화 버튼, 레벨업 버튼 신설
15차 배포 직후 사용자가 실제로 웹 시트를 써보고 5가지를 피드백: "캐릭터 삭제 버튼이 제대로 작동을 안해." / "캐릭터 초기화 버튼이 있으면 좋겠어." / "태그 입력 타이핑이 원활하지가 않아." / "핵심 자원 최대치 올리는건 레벨업 시에만 가능하게 해주고." / "레벨업 조건 달성할 때마다 레벨업 버튼을 누를 수 있게 추가하면 좋겠어."

**1) 태그 타이핑이 끊기는 원인과 수정**
경험 태그·침식 태그·소지품 태그 입력창이 매 keystroke마다 `save()`→`renderAll()`을 타면서 자기 자신이 속한 컨테이너의 `innerHTML`을 통째로 재생성하고 있었음 — DOM 노드가 파괴·재생성되니 입력 포커스가 매 글자마다 날아감(한 글자 치면 클릭해서 다시 포커스해야 다음 글자를 칠 수 있는 상태). 한글은 조합 입력이라 이 방식이면 조합 중간에 끊길 위험도 있었음. **"구조적 렌더"(캐릭터를 바꿀 때만 행 전체를 다시 그림)와 "값만 저장"(타이핑 중에는 모델과 localStorage만 갱신하고 DOM은 안 건드림 — 화면엔 이미 입력한 값이 있으므로 다시 그릴 필요가 없음)을 분리**해 해결. 이름·백스토리 등 일반 필드도 경량 저장 함수로 통일해 전반적인 타이핑 반응성을 개선.

**2) 삭제 버튼이 "제대로 작동 안 함"의 원인과 수정**
`deleteCharacterById`가 삭제 여부를 `confirm()`(브라우저 네이티브 다이얼로그)으로 물었는데, 이 파일이 저장하기 전 Cowork 대화 안에서 인라인 미리보기(iframe)로 먼저 보여지는 렌더링 경로에서는 샌드박스 정책상 `confirm`/`prompt`/`alert`가 조용히 차단되고 즉시 "취소"로 처리됐을 가능성이 높음 — 사용자 입장에선 "버튼을 눌러도 아무 반응이 없다"로 보였을 것. **네이티브 다이얼로그를 전부 제거하고, 시트 톤에 맞춘 커스텀 모달(확인/선택/입력/알림)로 교체** — 어떤 화면(미리보기든 실제 브라우저 탭이든)에서도 동일하게 동작하도록 함. GM PIN 확인, GM 잠금 설정, 캐릭터 삭제·초기화, 레벨업 자원 선택, 가져오기 실패 안내까지 전부 이 모달을 사용.

**3) 캐릭터 초기화 버튼**: 캐릭터 바에 "초기화" 버튼 신설 — 같은 슬롯을 유지한 채 이름·태그·자원·백스토리 전부를 빈 캐릭터로 되돌림 (삭제는 슬롯 자체를 없애며 최소 1개는 남아있어야 함 — 이제 마지막 캐릭터를 지우려 하면 "초기화를 대신 쓰라"는 안내가 뜸).

**4) 핵심 자원 최대치 = 레벨업 전용, 레벨업 버튼 신설**: 자원 행마다 있던 자유 "최대 +1" 버튼 제거(→ "레벨업 시 증가" 안내 문구로 대체). 레벨 박스 아래 **"🌟 레벨업!"** 버튼이 경험 태그 등급 합이 새 구간을 넘을 때마다 나타나고, 누르면 체력/정신력/피로도 중 하나를 골라 최대치 +1. 캐릭터마다 `levelUpsUsed`(이미 사용한 레벨업 횟수)를 저장해 "가능 횟수 = 현재 레벨 인덱스 − 이미 사용 횟수"로 계산 — 여러 구간을 한 번에 넘으면 그만큼 버튼을 여러 번 누를 수 있음. 기존 저장 데이터는 이미 손으로 올려둔 최대치만큼을 역산해 `levelUpsUsed`에 채워 넣어 이중 지급을 방지. 침식 태그 정화는 이번 변경과 무관하게 각 침식 태그 옆 "정화" 버튼으로 계속 언제든 가능(레벨업과 독립 — 아래 "미확인 사항" 참고).

**5) 검증**: Playwright로 (1) 태그 이름 칸에 실제 키 입력처럼 한 글자씩 입력해 포커스가 유지되고 최종 문자열이 정확한지, (2) 테스트 전체에서 네이티브 `dialog` 이벤트가 단 한 번도 발생하지 않는지(발생 시 실패 처리), (3) 삭제·초기화·GM PIN·레벨업 선택이 전부 커스텀 모달 버튼 클릭만으로 실제 동작하는지, (4) "최대 +1" 버튼이 어디에도 남아있지 않은지 확인 — 전부 통과.

### 17차 개정 — 핵심 자원 −/+ 버튼 ReferenceError 긴급 수정
16차 배포 직후 사용자가 브라우저 콘솔 에러를 그대로 전달: `Uncaught Error: Uncaught ReferenceError: p is not defined` / `Uncaught Error: Uncaught ReferenceError: max is not defined`.

**원인**: `renderResources()`가 체력/정신력/피로도 각 행의 −/+ 버튼을 만드는 부분에서 `onclick="setRes('${k}',Math.max(0,p[k]-1))"`처럼 `Math.max(0,p[k]-1)`이라는 **JS 소스 코드 텍스트를 템플릿 리터럴의 `${}`로 감싸지 않고 그대로** HTML 속성 문자열 안에 넣어놨음. 인라인 이벤트 핸들러는 클릭 시 전역 스코프에서 실행되는데, `p`(현재 캐릭터 객체)와 `max`(그 자원의 최대치)는 `renderResources()` 함수 내부에서만 존재하는 지역 변수라 전역에서는 찾을 수 없어 `ReferenceError`가 발생했음. 15~16차에서 정확히 같은 유형의 버그(`editErosion`/`editInventory`/`clearErosion` 등, "인라인 핸들러는 전역 스코프에서 실행되므로 지역 변수를 참조하면 안 된다"는 원칙)를 이미 한 차례 고쳤었는데, 이 두 버튼은 그 개정 범위에 포함되지 않아 원본 GPT 프로토타입 때부터의 버그가 그대로 남아있었음 — 태그 등급 상자(`onclick="setRes('${k}',${i+1})"`, 이미 `${}`로 안전하게 값만 삽입)는 정상 동작해서 다른 이상 신호가 없었고, 지금까지의 자동 테스트도 이 −/+ 버튼을 클릭해본 적이 없어서 발견되지 못하고 있었음.

**증상**: 핵심 자원(체력/정신력/피로도) 행의 −/+ 버튼을 눌러도 값이 전혀 바뀌지 않고 콘솔에만 에러가 찍힘. 토큰 상자를 직접 클릭하는 방식은 영향 없이 정상 동작.

**수정**: 계산 자체를 `${}` 안으로 옮겨 `onclick="setRes('${k}',${Math.max(0,p[k]-1)})"` / `onclick="setRes('${k}',${Math.min(max,p[k]+1)})"`처럼, 렌더 시점에 이미 계산된 **숫자 리터럴만** HTML 속성에 삽입되도록 수정 — 토큰 상자 `onclick`이 원래 쓰던 것과 동일한 안전한 패턴으로 통일.

**검증**: 신규 Playwright 테스트(`test_app3.py`)로 체력/정신력/피로도 3개 행 각각의 −/+ 버튼을 클릭해 값이 정상적으로 증감·원복되고, 그 과정에서 `pageerror`(ReferenceError 포함)나 네이티브 다이얼로그가 전혀 발생하지 않는지 확인. 기존 16차 회귀 테스트(`test_app2.py`)도 함께 재실행해 이번 수정이 타이핑·삭제·초기화·레벨업 등 다른 기능에 영향을 주지 않았음을 재확인 — 전부 통과.

### 18차 개정 — 웹 버전을 PDF 캐릭터 시트("character_sheet.html")의 구성·비주얼 그대로 이식 (앞/뒤 2페이지 구조)
사용자가 실제 PDF 출력물 이미지(앞면·뒷면)를 첨부하며 "웹 사이트 구성을 PDF 캐릭터 시트지 그대로 만들어 줄 수 있어?"라고 요청. `AskUserQuestion`으로 (1) 이식 범위(앞/뒤 2페이지 구조까지 전부 vs 지금 구조 유지+스타일만) (2) 뒷면 초상화 칸 처리(실제 업로드 기능 vs 디자인만) (3) 규칙 요약본 전체 추가 여부를 확인 — 전부 "추천" 옵션(① 2페이지 구조까지 전부 ② 이미지 업로드 기능 추가 ③ 10개 항목 전체 추가)으로 확정. 이번에 확인된 사실: 웹 버전은 10차 개정(아이콘 배지 스타일)을 한 번도 반영한 적이 없었음 — 10차는 PDF·엑셀에만 적용됐고, 웹은 GPT 프로토타입 당시의 단순한 디자인이 그대로 남아 있었음.

**1) 구조 전체 이식**: `#playerView`를 캐릭터 관리 툴바(기존 유지) + 스크롤 가능한 "종이 2장"(`.paper.front` / `.paper.back`, 각 210mm 폭, `character_sheet.html`의 mm·pt 단위와 클래스 구조를 거의 그대로 재사용)로 재구성.
- **앞면**: 로고(②) + PC이름/자기소개 + 노치 코너 레벨 배너(육각 클립패스, 기존 `#level`/`#tagSum` 로직 그대로 연결 + 그 아래 레벨업 버튼) · 태생 태그 3장(육각 "1" 배지 카드) · 경험 태그(진짜 `<table>`로 전환, 드롭다운 로직은 기존 그대로) · 침식 태그(해골 육각 배지 카드) · 핵심 자원(♥/✦/◐ 육각 배지 + 트래커 박스, 박스 직접 클릭으로 값 지정 + 보조 −/+ 버튼도 유지) · 판정(주사위 굴리기 + 10+/5~9/4- 참고 박스 + 점선 규칙 박스 3종) · 마법 물품(이름·전용 태그는 기존 그대로, "형태"(무기류·방어구류·마법도구류) 라디오는 PDF엔 있었지만 웹엔 없던 필드라 이번에 `magicForm`으로 신규 추가) · 장비 & 소지품(진짜 `<table>`로 전환 + 착용무기·방어구·화폐 4종을 한 줄 "gear-foot"으로 통합).
- **뒷면**: 로고 + "백스토리 카드" 제목 + PC이름 미러(읽기 전용, 앞면 입력값과 자동 동기화) · 초상화 박스(③) + 정보란(가치관/나이/키·몸무게/외모특징×2 — "외모특징" 칸이 원래 없어서 `look1`/`look2` 필드 신규 추가) · 상세 백스토리 · **마스터 비밀 메모 박스**(PDF는 종이를 물리적으로 "접는 선"으로 숨기는 개념이지만, 웹은 이미 15차에서 GM 세션 탭 + PIN 잠금이라는 더 안전한 방식으로 분리해 뒀으므로 실제 비밀 텍스트는 넣지 않고 "GM 세션 탭에서 PIN으로 보호되어 작성·열람됩니다" 안내만 보여주는 장식용 박스로 처리 — 15차의 보안 결정을 훼손하지 않기 위한 의도적 선택) · **규칙 요약본**(10개 항목, 2단 컬럼, `character_sheet.html`의 문구를 그대로 사용).
- 화면 상단에 "◆ 캐릭터 시트 — 앞면" / "◆ 백스토리 카드 — 뒷면" 작은 라벨을 프레임 바깥에 추가(스크롤 중 위치 파악용, 인쇄 시에는 숨김) — PDF에는 없는 웹 전용 내비게이션 보조 요소.
- GM 세션 탭(대시보드)은 이번 변경 대상에서 제외 — 요청이 "캐릭터 시트지"(플레이어 시트) 구성에 한정됐고, GM 대시보드는 애초에 종이 문서가 아닌 화면 전용 도구라 그대로 유지.

**2) 로고**: 기존 CSS로 그린 "✦ TAG & DICE" 텍스트 로고 대신, 프로젝트 파일의 실제 로고 이미지(`logo_transparent.png`, 용·주사위 그래픽)를 축소(세로 480px)·팔레트 압축(pngquant)해 약 72KB PNG로 최적화한 뒤 base64로 파일에 직접 내장(외부 파일 참조 없이 단일 HTML 파일 구조 유지). 앞/뒤 페이지 헤더에 동일하게 사용.

**3) 초상화 업로드 기능 (신규)**: 뒷면 초상화 박스를 클릭하면 이미지 파일을 선택 → `<canvas>`로 최대 480px로 축소 후 JPEG(품질 0.82)로 재인코딩 → `data:` URL로 캐릭터별 저장(`p.portrait`). 원본 이미지를 그대로 저장하면 localStorage 용량 한도(브라우저마다 다르지만 보통 5~10MB)를 쉽게 넘길 수 있어 업로드 시점에 축소·재압축하도록 설계했음. "✕ 제거" 버튼으로 삭제 가능. `localStorage.setItem` 실패(용량 초과 등) 시 조용히 실패하지 않도록 `persistQuiet()`에 try/catch + 안내 모달을 추가.

**4) 마법 물품 "형태" 필드 신규 추가**: PDF에는 있었지만 웹 프로토타입엔 원래 없던 필드 — 무기류/방어구류/마법도구류 라디오 버튼(`magicForm`)을 추가해 PDF와 항목 구성을 맞춤.

**5) 의도적으로 다르게 처리한 부분**:
- 헤더의 종족/배경/본능 "미니 요약 줄"(PDF `.head .misc`)은 웹에 옮기지 않음 — PDF는 한눈에 보는 요약 줄과 아래 태생 태그 카드가 서로 다른 빈칸(종이라 둘 다 손으로 적음)이지만, 웹은 값이 하나뿐이라 같은 값을 두 군데 보여주면 "어느 쪽이 진짜 입력칸인지" 혼동을 줄 수 있어 태생 태그 카드 쪽 한 곳에만 입력하도록 단순화.
- 소지품 태그 설명문은 PDF의 축약된 한 줄 대신 15차에서 추가한 상세 설명문을 그대로 유지(웹은 지면 제약이 없으니 더 친절한 설명이 낫다고 판단).
- 핵심 자원의 −/+ 버튼(16~17차에서 만든 것)은 PDF엔 없지만(종이라 손으로 칸을 채움), 트래커 박스를 직접 클릭해도 동일하게 값을 바로 지정할 수 있어 사실상 중복 기능임에도, 기존 사용자가 이미 쓰고 있었을 조작 방식을 임의로 없애지 않기 위해 작게 축소한 형태로 남겨둠.
- 인쇄(`window.print()`) 시 주사위 굴리기 카드(`.rollcard`)는 숨기고 10+/5~9/4- 참고 박스만 남도록 처리 — 인쇄 결과가 실제 `character_sheet.pdf`와 더 가깝게 보이도록 함.

**6) 검증**: 신규 Playwright 테스트(`test_app4.py`)로 다음을 확인 — 로고 base64 정상 삽입(앞/뒤 페이지 모두) · 이름/경험 태그 입력 타이핑 포커스 유지(회귀) · 레벨 공식 회귀 없음(그레이드3 태그 3개 → 합9 → Ⅱ) · 침식 카드 입력/정화 · 핵심 자원 육각 배지 노출 + 트래커 박스 클릭 + −/+ 버튼(ReferenceError 회귀 없음) · 주사위 굴리기 · 마법 물품 이름/전용태그/형태 라디오/사용 체크 · 소지품 테이블 10행 + 장비·화폐 6칸 · 뒷면 정보란(가치관·나이·키몸무게·외모특징×2) + PC이름 미러 동기화 · **초상화 업로드→축소·재인코딩→저장 및 제거** · **GM 비밀 메모 텍스트영역(`#secret`)이 플레이어 화면(`#playerView`) 안 어디에도 존재하지 않음**(보안 확인) · 규칙 요약본 10개 항목 노출 · 캐릭터 삭제/초기화(커스텀 모달) 회귀 · GM PIN 잠금(새로고침 후 오답 차단/정답 통과) 회귀 · 인쇄 미디어 에뮬레이션에서 앞/뒤 페이지 모두 정상 렌더 · 네이티브 다이얼로그·페이지 에러 0건. 전부 통과. 기존 `test_app.py`~`test_app3.py`는 이번 DOM 구조 개편으로 셀렉터가 옛 구조(`.experience-row`, `.erosion-row`, `.resource-row` 등)를 가리키게 되어 더 이상 유효한 회귀 게이트가 아님 — 참고 기록용으로만 남기고, `test_app4.py`가 현재의 표준 회귀 테스트임.

### 19차 개정 — 마스터 비밀 메모 삭제, PC 데스크톱 좌우 2단 배치, 육각 배지 아이콘 찌그러짐 수정
사용자가 실제 웹 시트를 써보고 세 가지를 한 번에 요청: "캐릭터 시트에 마스터 비밀 메모는 지워도 되지않을까?", "PC 웹 캐릭터 시트에서는 왼쪽(캐릭터 시트), 오른쪽(백스토리 카드) 이렇게 한 화면에 보이도록 배치해줘", "아이콘 찌그러짐 문제도 해결해줘." 세 요청 모두 웹 버전(`index.html`)에 한정해 적용 — 대화 맥락과 사용자의 표현("PC 웹 캐릭터 시트")이 모두 웹 버전만을 가리키고 있어, PDF·엑셀 산출물은 이번 라운드에서 손대지 않음.

**1) 마스터 비밀 메모 박스 완전 삭제**: 18차에서 만들어둔 뒷면의 장식용 안내 박스(`.gmnote`, "GM 세션 탭에서 PIN으로 보호되어 작성·열람됩니다" 문구만 있던 자리)를 통째로 제거. 이 박스는 애초에 실제 비밀 텍스트가 들어있던 적이 없어(15차 보안 결정으로 진짜 비밀 메모는 GM 세션 탭 + PIN 잠금에만 존재) 삭제해도 기능 손실이 없음을 확인하고 진행. 뒷면 레이아웃은 2단 그리드(백스토리 패널 + 34mm 폭의 메모 박스)에서 백스토리 패널이 전체 폭을 쓰는 단일 컬럼으로 단순화 — 초상화·기본정보·백스토리 입력 영역이 자연스럽게 더 넓어짐.

**2) PC 데스크톱에서 앞/뒤 페이지 좌우 동시 표시**: 기존엔 앞면을 본 뒤 아래로 더 내려야 뒷면이 보이는 세로 스택 구조였는데, 데스크톱처럼 화면이 넓을 때는 앞면(좌)·뒷면(우)이 나란히 한 화면에 보이도록 변경(`papers-scroll`을 세로 스택 → 가로 flex 배치). 950px 이하(모바일·태블릿)에서는 두 페이지(각 210mm)가 나란히 들어갈 공간이 없으므로 자동으로 기존처럼 세로 스택으로 돌아감. 인쇄는 화면 배치와 무관하게 항상 앞면 → 뒷면 순서로 별도의 A4 페이지 2장이 되어야 하므로, 인쇄 스타일에서 레이아웃을 강제로 원래의 세로 블록 구조로 되돌리는 처리를 추가 — 이 과정에서 페이지를 감싸는 구조가 하나 늘어나며 "마지막 페이지 뒤에는 빈 페이지를 넣지 않는다"는 기존 규칙이 조용히 깨질 뻔한 것을 발견해 함께 수정(더 이상 앞면이 "마지막 페이지"로 잘못 인식되지 않도록 선택자 보정).

**3) 육각 배지 아이콘 찌그러짐 수정**: 실제 화면을 캡처해서 원인을 확인해보니 서로 다른 두 가지 문제가 섞여 있었음.
- 첫째, 체력♥·정신력✦·침식☠ 배지는 인쇄용 PDF와 똑같은 물리 치수(5.6mm 배지, 아주 작은 글자)를 화면에도 그대로 쓰고 있었는데, 인쇄물은 실제 종이 해상도가 높아 괜찮지만 일반 모니터(96dpi)에서는 픽셀 수가 너무 적어 뭉개져 보였음. 게다가 이 기호들은 본문 서체(Noto Serif KR)에 없는 글자라 시스템 대체 서체로 넘어가는데, 그 대체 서체에 원래 지정했던 최고 굵기(900, black)가 없으면 브라우저가 억지로 획을 부풀려 그리면서(인조 볼드) 더 뭉개지는 현상까지 겹쳐 있었음. → 화면에서만 배지를 더 키우고(5.6mm→9mm) 굵기를 실제 존재하는 굵기(700)로 낮춰서 해결. 인쇄용 치수는 전혀 건드리지 않아 PDF 저장 결과물은 이전과 동일함.
- 둘째, 피로도 아이콘(반원 모양, ◐)은 위 방식으로 키워봐도 여전히 얇은 초승달 모양으로 깨져 보였음 — 크기 문제가 아니라 이 서체에서 이 글자 자체가 얇게 그려지도록 디자인되어 있는 것으로 보임. 크기를 키운다고 해결되는 문제가 아니라서, 아예 원 전체를 채운 모양(●)으로 아이콘 자체를 교체함. 이 부분은 화면 전용 스타일이 아니라 실제 데이터를 바꾼 것이라 웹 시트의 인쇄 결과물에도 ●로 반영됨 — 화면과 인쇄가 다시 하나로 일치함.
- **참고**: 이 반원(◐) 글자가 깨지는 현상은 브라우저 폰트 렌더링 자체의 문제로 보여서, 같은 방식(mm 단위 + 브라우저 렌더링)으로 만들어진 `character_sheet.html`/PDF 원본에도 혹시 같은 문제가 있는지는 이번에 확인하지 않았음 — 아래 "남은 미확인 사항" 12번에 추가해둠.

**4) 검증**: `test_app4.py`를 갱신해 재실행 — 마스터 비밀 메모 박스(`.gmnote`)가 플레이어 화면 어디에도 남아있지 않은지, 데스크톱 폭(1800px)에서 앞/뒤 페이지가 실제로 같은 높이에서 좌우로 나란히 배치되는지, 좁은 화면(480px)으로 줄이면 다시 세로 스택으로 바뀌는지, 육각 배지가 화면에서 찌그러짐 없이 알아볼 수 있는 최소 크기(28px) 이상으로 렌더되는지 전부 확인. 기존 회귀 항목(타이핑 포커스, 레벨 공식, GM PIN 잠금, 삭제/초기화, GM 비밀정보 비노출 등)도 함께 재실행해 이번 변경이 다른 기능에 영향을 주지 않았음을 재확인 — 네이티브 다이얼로그·페이지 에러 0건으로 전부 통과.

### 20차 개정 — PC 좌우 배치가 실제 화면 폭에서 잘리던 문제 수정 (19차 배포 직후 발견)
사용자가 배포된 파일을 실제로 열어본 화면 스크린샷을 첨부하며 "이렇게 잘려보이게 하지말고 전체적으로 보이게 해줬으면 해"라고 요청.

**원인**: 앞/뒤 페이지를 좌우로 배치하려면 가로로 `210mm×2 + 간격 16px ≈ 1603px`가 필요한데, 시트를 감싸는 `.wrap` 컨테이너가 `max-width:1420px`(패딩 제외 약 1380px)로 제한돼 있어서 **1800px짜리 넓은 브라우저 창에서도** 뒷면 오른쪽 일부가 원래부터 잘리고 있었음. 19차 검증 때는 "앞/뒤가 서로 나란히 있는지"(상대 위치)만 확인했지 "그게 실제로 화면 안에 다 들어오는지"(절대적으로 안 잘리는지)는 따로 확인하지 않아서 이 부분을 놓쳤음 — 게다가 사용자가 실제로 보고 있던 화면은 Cowork 대화 안의 미리보기 패널이라 일반 브라우저 탭보다 폭이 더 좁았을 가능성이 높음.

**수정**: 두 페이지를 감싸는 컨테이너가 항상 콘텐츠 원래 크기(1603px, 모바일에서는 페이지 1장 폭)를 유지하도록 만든 다음, 그 원래 크기와 실제로 화면에서 쓸 수 있는 폭을 비교해서 필요할 때만 두 페이지를 통째로 균일하게 축소하는 `fitPapers()` 로직을 새로 추가함(절대 확대는 하지 않고 최대 1배). 창 크기가 바뀌거나 시트 내부 구조가 바뀌면(예: 레벨업 버튼이 나타나 높이가 바뀔 때) `ResizeObserver`가 감지해서 자동으로 다시 계산됨. 인쇄와 이미지 저장은 이 화면용 축소와 무관하게 항상 원래 크기(배율 1)로 처리되도록 별도로 예외 처리함.
- 이 수정 덕분에 18차부터 "미확인 사항"으로 남아있던 모바일 가로 스크롤 문제도 부수적으로 해결됨 — 모바일에서도 페이지 1장이 화면 폭에 맞게 자동으로 축소되어 가로 스크롤 없이 전체가 보임. 다만 그만큼 화면이 아주 좁을 때(스마트폰 등)는 19차에서 화면 전용으로 키워둔 육각 배지 아이콘도 함께 축소되어, 아주 좁은 화면에서는 아이콘이 다시 작아질 수 있음 — 다만 19차에서 고친 "굵기 문제"(인조 볼드로 뭉개지는 것)와 "글리프 문제"(피로도 아이콘이 초승달로 깨지는 것) 자체는 크기와 무관하게 그대로 유지되므로, 작아지더라도 이전처럼 뭉개지거나 깨져 보이지는 않음.

**검증**: `test_app4.py`에 실제 이번 버그를 재현하는 조건(1800·1420·1300·1000·480px 등 다양한 화면 폭)에서 앞/뒤 페이지의 경계가 화면 밖으로 한 픽셀도 벗어나지 않는지 직접 확인하는 항목을 추가 — "나란히 배치되어 있는지"만으로는 이번 문제를 못 잡는다는 걸 실제로 겪었기 때문에, 기존의 상대 배치 확인과는 별개로 유지함. 인쇄 시 화면용 축소가 적용되지 않고 항상 원래 배율로 리셋되는지도 함께 확인. 축소된 상태에서도 버튼 클릭·타이핑 같은 상호작용이 좌표 오차 없이 정상 동작하는지 재확인. 전체 재실행 결과 네이티브 다이얼로그·페이지 에러 0건으로 전부 통과.

### 21차 개정 — 화면 높이까지 고려한 완전 자동 축소로 스크롤바 자체를 제거 (20차 배포 직후 발견)
사용자가 "브라우저 창에 실제로 화면 안에 다 들어와야지 스크롤바가 생기면 안돼. 굳이 있을 필요도 없고. 캐릭터 시트랑 백스토리 카드가 조금 더 가로로 넓어져도 상관없어"라고 요청. 20차에서 가로 잘림은 해결됐지만, 세로 스크롤은 여전히 남아있었다는 지적.

**원인**: 20차의 `fitPapers()`는 **가로 폭만** 기준으로 축소 비율을 계산했음(`scale = 화면에서 쓸 수 있는 폭 / 콘텐츠 원래 폭`). 세로 높이는 전혀 고려하지 않았기 때문에, 화면이 넓기만 하고 키가 크지 않은 창(노트북 브라우저, Cowork 미리보기 패널 등 흔한 경우)에서는 가로는 딱 맞아도 세로가 넘쳐서 전체 페이지가 스크롤되는 문제가 그대로 남아있었음. 실제로 확인해보니 1366×768(흔한 노트북 해상도) 같은 크기에서도 세로 스크롤이 발생하고 있었고, 1800×1400처럼 아주 넉넉한 창이 아니면 대부분 세로 스크롤이 필요한 상태였음.

**수정**:
1. `fitPapers()`가 가로 폭뿐 아니라 **세로로 실제 쓸 수 있는 높이**(창 높이 − 시트 위쪽의 상단바·툴바가 차지하는 공간 − 여백)까지 함께 계산해서, 가로 기준 축소 비율과 세로 기준 축소 비율 중 **더 작은 쪽**을 최종 배율로 사용하도록 변경 — 이제 가로든 세로든 어느 한쪽이라도 넘치면 그에 맞춰 전체가 축소되므로, 어느 화면 크기에서도 스크롤바 자체가 생기지 않음.
2. 사용자가 "카드가 넓어져도 상관없다"고 한 부분은, 시트를 감싸는 `.wrap` 컨테이너의 최대 폭 제한을 `1420px → 1680px`로 넓히는 것으로 반영 — 두 페이지가 나란히 필요로 하는 실제 폭(약 1603px)을 여유 있게 넘는 값이라, 창이 그 정도로 넓을 때는 더 이상 인위적인 폭 제한 때문에 축소되지 않고 원래 크기(배율 1) 그대로, 혹은 그에 가깝게 표시됨. 즉 "가로 여유가 있으면 굳이 줄이지 않고 넓게 써도 된다"는 뜻으로 해석해 반영함.
3. 레벨업 버튼처럼 시트 내부 콘텐츠가 바뀔 때뿐 아니라, 툴바(캐릭터 선택바 등)의 높이가 바뀌는 경우(좁은 화면에서 버튼이 다음 줄로 넘어가는 경우 등)도 감지해서 다시 계산하도록 `ResizeObserver`가 감시하는 대상에 툴바를 추가함.
4. **트레이드오프(사용자에게 투명하게 공유할 부분)**: "스크롤바를 절대 만들지 않는다"를 우선하다 보니, 창이 넓기만 하고 키가 작은 경우(예: 1366×768) 시트가 20차 때보다 더 작게(약 43% 크기) 줄어들 수 있음 — 세로 공간이 부족하면 그만큼 강하게 축소해야 스크롤 없이 다 보이기 때문. 극단적으로 창이 작아지는 것까지 막는 최소 배율(0.15)은 안전장치로만 넣어뒀고, "이 정도는 읽기 편해야 한다"는 기준으로 넣은 하한선은 아님 — 실제로 써보고 너무 작게 느껴지면, "스크롤바 완전 금지"보다 "어느 정도 크기 이상은 유지하고 대신 약간의 스크롤은 허용" 쪽으로 절충하는 것도 가능하니 알려주면 됨.

**검증**: `test_app4.py`의 잘림 검증 항목을 가로 폭만이 아니라 가로×세로 9가지 조합(1800×1400, 1680×900, 1420×900, 1366×768, 1300×800, 1200×700, 1000×600, 900×650, 480×800)으로 확장하고, 페이지 잘림 여부뿐 아니라 `document.documentElement`의 `scrollWidth`/`scrollHeight`가 `clientWidth`/`clientHeight`를 넘지 않는지(=스크롤바가 전혀 생기지 않는지)를 직접 확인하도록 항목을 추가함 — 전부 통과. 추가로 가장 작은 배율(약 0.17배)이 적용되는 창 크기에서 텍스트 입력·버튼 클릭이 좌표 오차 없이 정상 동작하는지도 별도로 확인함(정상 동작 확인).

### 22차 개정 — "스크롤바 없음"보다 가독성 우선: 최소 배율 하한 신설 (21차 배포 직후 발견)
사용자 피드백: "화면 비율이랑 폰트가 전체적으로 너무 작아서 보기가 힘들어." `AskUserQuestion`으로 절충 방향을 확인한 결과 **"최소 크기 보장 + 부족하면 스크롤"**로 확정(다른 선택지는 "자동 축소 없이 항상 실제 크기" / "자동 맞춤 + 수동 확대·축소 버튼"이었음).

**원인**: 21차는 "스크롤바가 절대 생기면 안 된다"를 우선해 가로·세로 모두 사실상 하한 없는(0.15) 축소를 허용했음. 실측해보니 1366×768(흔한 노트북 해상도)처럼 평범한 창에서도 배율이 약 0.4~0.6까지 떨어졌는데, 이 시트는 애초에 A4 인쇄 기준 6~9pt대의 작은 글자를 화면 전용 확대 없이 그대로 쓰고 있어서, 거기서 다시 그만큼 축소되면 실제로 읽기 어려운 수준이 됨 — "스크롤 완전 제거"라는 목표 자체가 가독성을 해치는 부작용을 냄.

**수정**: `fitPapers()`에 `MIN_COMFORTABLE_SCALE=0.85` 하한을 추가하되, 화면 배치 모드에 따라 다르게 적용.
- **데스크톱/태블릿(앞뒤 페이지 좌우 2단 배치 모드)**: 배율이 0.85 밑으로는 내려가지 않도록 하고, 그 결과 화면에 다 안 들어가면(가로든 세로든) 이제는 스크롤로 나머지를 보게 함 — "스크롤 없음"보다 "읽을 수 있는 크기"를 우선.
- **모바일(950px 이하, 페이지 1장이 세로로 쌓이는 모드)**: 이 하한을 적용하지 않고 기존처럼 가로 폭을 항상 100% 우선 준수 — 이미 좁은 폰 화면에 가로 스크롤까지 얹는 건 세로 스크롤보다 더 나쁜 경험이라고 판단해, 20차의 "모바일 가로 스크롤 없음" 보장은 그대로 지킴.
- 지금이 어느 모드인지는 `.papers-scroll`의 계산된 `flex-direction` 값(950px CSS 미디어 쿼리와 자동 연동)으로 판별해서, 950이라는 값을 JS에 다시 하드코딩하지 않도록 함.

**트레이드오프(투명하게 공유)**: 데스크톱이라도 창이 충분히 넓지 않으면(대략 1360px 미만) 이제 뒷면 카드 오른쪽 일부를 보려면 가로로 살짝 스크롤해야 할 수 있음. 20차 이전의 "잘려서 아예 못 보던" 상태와 달리 스크롤하면 언제든 전부 볼 수 있는 상태지만, 화면만 보면 비슷한 인상을 줄 수 있어 이 문서와 사용자 안내에 명확히 남겨둠. 실제로 1366×768과 1000×700에서 스크린샷을 찍어 육안으로 검토 — 1366×768은 앞/뒤 모두 스크롤 없이 읽기 편한 크기로 나왔고, 1000×700은 앞면은 완전히 보이지만 뒷면 오른쪽 정보란 일부가 화면 밖으로 나가 가로 스크롤이 필요한 상태임을 확인함.

**검증**: `test_app4.py` 17b 항목을 3그룹으로 재구성 — (a) 여유로운 창(1800×1400)은 여전히 스크롤바가 전혀 없어야 함, (b) 데스크톱 폭이지만 빡빡한 창들(1680×900~1000×600)은 배율이 정확히 0.85(오차 0.01 이내)로 고정되는지, (c) 모바일 폭(900×650, 480×800)은 항상 스택 모드로 전환되고 가로 방향은 여전히 전혀 잘리지 않는지. 전부 통과.

### 23차 개정 — 창에 여유가 있으면 최대 175%까지 확대 (가로 폭 기준, 세로 스크롤 허용) (22차 배포 직후 발견)
사용자 피드백: Cowork 미리보기 스크린샷(일반/최대화 상태)과 함께 "여기서, +75% 정도 더 크게 확대되서 보이게 할 수 없을까".

**원인**: 이번 건은 원인이 세 겹이었음.
1. 22차까지는 배율 상한이 사실상 1(원본 크기)로 고정 — 20차에서 정한 "절대 확대는 하지 않는다" 원칙 때문에, 창이 아무리 넓어도 원본보다 크게 보여준 적이 없었음.
2. 상한만 올리는 것으로는 부족했음: `scroll.style.transform = scale<0.999 ? scale(...) : "none"` 분기가 "배율 0.999 이상이면 변형 없음(=원본 그대로)"이라는, 배율이 1을 넘을 수 없던 시절의 가정을 그대로 갖고 있어서, 배율이 예컨대 1.3으로 계산되어도 실제로는 transform이 적용되지 않고 조용히 원본 크기로 렌더링되는 버그가 있었음(코드 작성 중 자체 발견, 배포 전에 수정).
3. `.wrap{max-width:1680px}`도 병목 — 2단 배치 시 필요한 실제 폭(~1603px) 기준 175%는 약 2845px인데 컨테이너 자체가 1680px로 막혀 있어 상한을 아무리 올려도 물리적으로 도달 불가능했음.
4. 위 세 가지를 전부 고친 뒤에도, 사용자가 첨부한 스크린샷과 동일한 2560×1400 해상도로 직접 측정하니 배율이 0.868배 → 0.868배로 전혀 변하지 않았음. 원인은 이 시트의 세로 자연 높이(~1442px)가 웬만한 모니터의 실사용 가능 높이(헤더·툴바를 제외하면 보통 1200~1300px대)보다 항상 더 크다는 것 — "가로·세로 중 더 빡빡한 쪽에 맞추기" 방식에서는 세로가 항상 병목이 되어, 가로로 아무리 여유가 있어도 전혀 활용되지 못하는 구조였음.

**수정**:
1. `MAX_SCALE=1.75` 상수를 추가하고 배율 계산의 상한을 1 → 1.75로 확장.
2. `scroll.style.transform` 결정 로직을 `scale<0.999 ? ... : "none"`에서 `Math.abs(scale-1)<0.001 ? "none" : scale(...)`로 수정 — 1보다 작을 때뿐 아니라 1보다 클 때도 정상적으로 변형이 적용되도록 함.
3. `.wrap{max-width:1680px}` → `2900px`로 확대.
4. **(핵심) 데스크톱/2단 모드의 배율 계산 방식 자체를 변경**: "가로·세로 중 더 빡빡한 쪽에 맞추기"에서 **"가로 폭 기준으로만 계산하고, 그 결과 세로가 넘치면 스크롤 허용"**으로 바꿈. 세 가지만 고치고 끝냈다면 실제 모니터에서는 체감 변화가 거의 없었을 것이므로, `AskUserQuestion`으로 트레이드오프를 직접 확인(옵션: 가로 기준 최대 확대·절충안·현행 유지 3가지 제시) → **"가로 기준 최대 확대, 세로 스크롤 감수"**로 확정. 모바일(스택 모드)은 원래부터 가로가 항상 상한이라 변경 없음.

**트레이드오프**: 데스크톱 모드에서는 이제 창이 넓기만 하면(높이와 무관하게) 배율이 커지고, 그만큼 시트 전체를 보려면 세로 스크롤이 필요해짐 — 21~22차가 줄여온 "세로 스크롤"이 다시 늘어나는 방향의 변경으로, "스크롤 없음"보다 "크고 읽기 편한 시트"를 우선한다는 트레이드오프를 사용자가 직접 선택한 것임. 예: 사용자의 2560×1400 화면에서는 배율이 0.868배 → 1.572배(약 +81%, 요청한 "+75%"에 근접)로 커지지만, 시트 전체를 보려면 세로로 화면 높이의 약 1.7배 분량을 스크롤해야 함. 가로 스크롤은 이전과 동일하게 어떤 경우에도 발생하지 않음(배율이 가로 기준으로 계산되므로 구조적으로 가로 초과가 불가능).

**검증**: `test_app4.py` 17b 항목을 전면 재작성.
- (a) 1800×1400: 배율이 가로 기준(~1.098)으로 올라가고, 세로 스크롤이 실제로 발생하되 가로 스크롤은 없음을 확인.
- (b) 1680×900~1000×600(6개 창 크기): 가로 기준 배율이 0.85 하한보다 큰 구간(1680→약 1.02, 1420→약 0.86)과 하한에 걸리는 구간(1366 이하→0.85 고정)을 실측값과 대조, 항상 가로 무손실인지 확인.
- (c) 900×650, 480×800(모바일 폭): 기존과 동일하게 스택 모드 + 가로 무손실 유지 확인(회귀 없음).
- (d) 신규: 2200×1200(부분 확대, 상한 미도달)과 3200×2900(상한 1.75 고정)에서 배율과 가로 무손실 확인. 3200×2900(배율 1.75) 상태에서 이름 입력창에 실제로 클릭+타이핑하고 2d6 굴리기 버튼을 클릭해 정상 반영되는지까지 확인 — 확대된 상태에서도 클릭/포커스 위치 계산(hit-testing)이 정상 동작함을 실증.
- 전체 스위트 5회 연속 재실행으로 큰 뷰포트 전환 시 타이밍 이슈(최초 1회 확대 상한 미도달로 실패한 사례 발견 → 대기시간을 150ms에서 300ms로 늘려 해결)가 재발하지 않음을 확인.
- 추가로 사용자의 실제 스크린샷과 동일한 2560×1400 해상도로 스크린샷을 찍어 육안으로 검토, 실제로 시트가 훨씬 크게 보이는 것을 확인.

### 24차 개정 — "확대는 유지, 세로 스크롤 감수" → "세로 스크롤 완전 제거"로 재변경 (23차 배포 직후 발견)
사용자가 23차 결과물을 실제로 열어본 화면 스크린샷(스크롤바가 보이는 상태)을 첨부하며 "화면 비율은 좋은데 왜 굳이 필요없는 스크롤바가 추가되는지 모르겠어"라고 질문.

**원인**: 버그가 아니라 23차에서 사용자가 직접 선택한 "가로 기준 최대 확대, 세로 스크롤 감수"의 정확한 수학적 결과였음. 실제로 재현해보니(사용자 스크린샷과 동일한 2624×1400) 배율 1.612배, 세로 초과분 1073px(화면 높이의 75%)이 정확히 발생하고 있었음 — 계산상 이 창 높이에서 세로 스크롤을 완전히 없애려면 배율이 0.868배(오히려 원본보다 작음)여야 하므로, "지금 크기 그대로 스크롤만 없앤다"는 애초에 성립할 수 없는 조합이었음. 크기와 스크롤량이 정확히 같이 움직이는 값이라는 걸 `AskUserQuestion`으로 구체적인 수치(0.87배/스크롤 0% ~ 1.75배/스크롤 75%)와 함께 다시 확인.

**수정**: 4가지 선택지(확대 유지+스크롤 최소화 절충안 / 스크롤 완전 제거 / 원본 100% 고정 / 현재(23차) 그대로 유지) 중 **"스크롤 완전히 제거"**를 선택함에 따라, 데스크톱/2단 모드의 배율 공식을 23차의 "가로 폭 기준"에서 다시 **`min(가로 배율, 세로 배율)`**(21~22차와 동일한, 스크롤 자체가 생기지 않는 방식)로 되돌림. 다만 23차에서 올린 `MAX_SCALE=1.75` 상한과 `scale>=1`일 때도 transform이 정상 적용되도록 한 버그 수정은 그대로 유지 — 창이 가로·세로 양쪽 모두 실제로 넉넉할 때(예: 매우 크고 세로로도 긴 모니터)는 여전히 원본보다 확대될 수 있고, 이번에 되돌린 것은 "세로 공간이 부족한데도 가로만 보고 억지로 키우는" 부분뿐임.

**트레이드오프(사용자에게 명확히 전달)**: 사용자의 실제 창처럼 "가로는 넓지만 세로는 넉넉하지 않은" 형태의 모니터에서는, 이번 되돌림으로 인해 **23차 이전(22차)과 사실상 동일한 크기(약 0.87배)로 돌아감** — 즉 이번 라운드로 시작된 "+75% 확대" 요청은 이런 화면 비율에서는 시각적으로 거의 원점으로 돌아간 셈. 대신 가로로 넓은 공간을 시트가 실제로 채우지는 못하고 다시 여백으로 남게 됨(23차 이전과 동일한 모습). 세로로도 충분히 큰 창(예: 세로로 길게 늘인 창, 초고해상도 모니터)에서는 여전히 확대 효과를 볼 수 있음.

**검증**: `test_app4.py` 17b 항목을 다시 22차 방식(그룹 a/b/c: 여유 창은 완전 무스크롤, 데스크톱 빡빡한 창은 배율 정확히 0.85, 모바일은 가로 무손실)으로 되돌리고, 그룹 d는 "가로·세로 모두 진짜 넉넉한 창"(3200×1800 부분 확대, 3200×2900 상한 1.75 고정)에서 양방향 모두 스크롤바가 없는지 확인하도록 재구성 + 확대 상태에서의 클릭/타이핑 상호작용 확인은 유지. 3회 연속 재실행 통과. 추가로 사용자의 실제 스크린샷과 동일한 2624×1400에서 스크린샷을 찍어 배율이 정확히 0.868배로 돌아오고 스크롤바가 사라졌음을 육안으로 확인.

### 25차 개정 — 축소된 시트가 한쪽으로 쏠리는 "빈 공간" 문제 수정 (24차 배포 직후 발견)
사용자가 24차 결과물을 다른 도구로 손보려 시도한 흔적이 담긴 스크린샷(별도 브라우저 탭에서 일반적인 CSS 조언을 참고해 수정을 시도)을 첨부하며 "이 비율이랑 빈공간 문제를 어떻게 해결하면 좋을까. 수정하면 할 수록 처음보다 더 이상해지는거 같아"라고 질문.

**원인**: 20~24차에서 다뤄온 "배율(크기)" 문제와는 별개로, 지금까지 손대지 않았던 문제였음. 시트를 담는 컨테이너(`.papers-viewport`)는 폭이 넉넉한 `.wrap`(최대 2900px) 안에서 항상 왼쪽 끝에 붙어 있었고, 축소된 콘텐츠보다 컨테이너가 넓게 남을 때 그 여백을 중앙으로 분배하는 규칙이 없었음. 특히 24차 공식에서는 "세로 공간이 부족해 배율이 가로 기준보다 작게 잡히는" 경우가 흔한데, 이때 축소된 시트 두 장이 왼쪽에 붙고 남는 폭 전부가 오른쪽 한쪽에만 쌓였음 — 정확히 스크린샷에서 지적된 그 여백.

**참고**: 사용자가 함께 전달한 CSS 수정 제안(`.wrap`을 1400px로 축소, 존재하지 않는 `.sheet`/`.grid-main` 클래스 수정 등)은 실제 코드와 값·클래스명이 맞지 않아 적용하지 않았고, 그대로 적용했다면 20차에서 고쳤던 2단 모드 가로 잘림 버그가 재발할 뻔했음(2단 모드 최소 요구 폭 ≈1603px > 1400px). 이 사실을 먼저 사용자에게 설명한 뒤, 진짜 원인인 "정렬" 문제를 별도로 진단.

**중요**: 23~24차의 "확대냐 세로 스크롤 제거냐"는 사용자가 직접 골라야 하는 트레이드오프였지만, 이번 "빈 공간" 문제는 손해 볼 선택지가 없는 순수한 정렬 버그라서 이번엔 다시 여쭤보지 않고 바로 수정함.

**수정**: (1) `.papers-viewport`에 `margin:0 auto`를 추가해 컨테이너가 `.wrap` 안에서 중앙 정렬되도록 하고, (2) `fitPapers()`가 배율을 계산할 때마다 축소된 콘텐츠의 실제 폭을 `viewport.style.width`에도 반영하도록 해 `margin:auto`가 실제로 작동할 폭 차이(컨테이너 폭 < `.wrap` 폭)를 만들어줌.

**부작용과 재수정**: 폭을 명시적으로 고정하는 방식이 새 버그를 만들었음 — 넓은 창에서 한 번 계산된 뒤 좁은 창으로 줄이면, 직전에 고정해둔 폭이 저절로 줄지 않아 다음 계산의 "사용 가능한 폭" 측정값이 실제보다 부풀려진 채 읽히는 자기참조 오류가 발생. 이 상태로 좁은 창(480×800)에서 시트가 오히려 가로로 넘치는 회귀가 테스트에서 발견됨. `fitPapers()` 맨 앞에서 매 계산 시작 시 `viewport.style.width`를 먼저 초기화한 뒤 측정하도록 수정해 해결.

**검증**: `test_app4.py`에 새 테스트 블록 (e) 추가 — 가로는 넓지만 세로가 부족해 배율이 가로 기준보다 작게 잡히는 창(2400×1000)에서 ① 실제로 배율이 1보다 작은지 ② 좌우 여백이 5px 이상 존재하면서 서로 3px 이내로 동일한지(중앙 정렬 확인) ③ 좁은 창(480×800)을 거쳤다가 같은 크기(2400×1000)로 돌아와도 배율·폭이 그대로인지(자기참조 버그 재발 방지)를 확인. 전체 스위트 8회 연속 재실행(1차 수정 직후 5회 + 회귀 테스트 추가 후 3회) 통과, 매번 네이티브 다이얼로그·페이지 에러 0건. 2400×1000 스크린샷에서 좌우 여백이 각각 518.5px/518.6px로 사실상 동일함을 육안으로도 확인(수정 전 상태를 재현한 비교 스크린샷에서는 좌측 20px·우측 1017px로 한쪽에 쏠려 있었음).

### 26차 개정 — 화면 레이아웃 전면 재설계: "종이를 축소해서 보여주기"를 버리고 진짜 반응형 웹으로 (25차 배포 직후, 사용자 요청)
사용자가 "컨텍스트에 올린 인덱스 파일로 다시 처음부터 만들어야겠는데"라고 요청. 먼저 확인해보니 프로젝트 문서의 `index.html`은 사용자가 처음 올렸던 GPT 원본 프로토타입이 아니라 매 라운드 덮어써 온 최신(25차) 버전이었고(원본은 세션 기록에서 복구 가능함을 확인), 그 사실과 함께 근본 원인을 설명한 뒤 `AskUserQuestion`으로 방향을 확인 → **"웹 전용으로 새로 설계"** + **"인쇄/PDF 저장은 계속 필요"**로 확정.

**근본 원인(20~25차가 여섯 번 반복된 이유)**: 이 시트는 A4 인쇄용 종이(210mm 고정 폭, mm·pt 단위)를 화면에서 `transform:scale()`로 통째로 축소해 보여주는 구조였음. 이 방식에서는 **크기·스크롤·여백이 전부 배율이라는 단 하나의 숫자에 묶여** 있어서, 하나를 고치면 반드시 다른 하나가 틀어짐. 20차(가로 맞춤) → 21차(세로까지, 너무 작아짐) → 22차(최소 배율 하한) → 23차(1.75배 확대, 세로 스크롤 발생) → 24차(스크롤 제거, 크기 원위치) → 25차(여백 쏠림)가 전부 같은 구조적 제약에서 파생된 증상이었음. 인쇄용 종이와 화면용 페이지는 애초에 서로 다른 기하 구조를 원하므로, 하나의 기하 구조를 공유하는 한 이 반복은 끝나지 않음.

**수정 — 화면과 인쇄에 각자의 기하 구조를 부여**:
1. **인쇄는 그대로 둠**: 기존 mm·pt 기반 규칙 전체를 손대지 않고 유지 → "인쇄 / PDF 저장" 결과물은 이전과 완전히 동일.
2. **화면은 새로 작성**: 동일한 DOM에 `@media screen` 블록으로 완전히 새로운 유동형 레이아웃을 부여. 210mm 고정 폭 → 유동 폭, mm·pt 치수 → px 기반 웹 치수(본문 14px, 제목 16px 등 실제로 읽히는 크기), 두 페이지 배치는 `repeat(auto-fit,minmax(min(100%,560px),1fr))` 그리드로 전환 — 공간이 있으면 좌우 2단, 없으면 자동으로 세로 1단이 되며 **중단점(breakpoint)도 JS도 필요 없음**.
3. **`fitPapers()` 및 전체 축소·확대 로직 완전 삭제**(약 6,600자): `transform:scale`, `ResizeObserver`, `MIN_COMFORTABLE_SCALE`/`MAX_SCALE`, viewport 폭·높이 고정 등 20~25차에 걸쳐 쌓인 기계장치를 전부 제거. 이제 레이아웃에 관여하는 JS는 한 줄도 없음.
4. 부수적으로 함께 정리한 것: 인쇄 시에도 적용되던 `@media(max-width:950px)` 블록을 `@media screen and (...)`으로 한정(A4 페이지 폭 794px는 950px 미만이라 실제 프린터에서는 본문이 1단으로 무너질 수 있었음), 인라인 mm 여백·퍼센트 열 너비를 클래스로 이관, 뒷면의 남는 높이를 백스토리 입력칸이 흡수하도록 처리, `exportImage()`에서 불필요해진 transform 저장·복원 제거.

**발견하고 고친 문제 2건**: (a) 인라인 스타일을 클래스로 옮기자 `h2.sec`(0,1,1)가 `.sec-gap`(0,1,0)를 이겨 인쇄 여백 3.4mm가 조용히 사라짐 — `h2.sec.sec-gap`으로 특이성을 맞춰 해결(인쇄 기준선 대조로 발견). (b) 경험 태그 "유형" 열이 인라인 16% 폭 탓에 실제 화면 글꼴에서 54px로 좁아져 드롭다운이 "ㅈ ∨"로 잘림 — 화면에서는 고정 px 폭으로 전환.

**트레이드오프(명확히 전달)**: 이제 시트가 읽을 수 있는 크기로 렌더되므로 **세로 스크롤은 정상적으로 발생**함(1600px 폭 기준 페이지 높이 약 2,175px). 24차에서 "세로 스크롤 완전 제거"를 선택했던 것과는 방향이 다르지만, 그때의 스크롤은 "고정 크기 그림이 창을 넘치는" 스크롤이었고 지금은 일반적인 웹 페이지의 스크롤임 — 대신 글자가 창 크기에 따라 작아지는 일이 완전히 사라짐. 가로 스크롤은 어떤 크기에서도 발생하지 않음.

**검증**:
- **인쇄 동일성**: 재설계 전 인쇄 미디어 기준선(치수 18종 + 전체 스크린샷)을 저장해두고 재설계 후 대조 — 앞/뒤 페이지 크기, 본문 그리드 열 너비, 규칙 요약본 단 수 등 **전 항목 완전 일치**. 픽셀 비교에서 남은 차이는 0.5px 오프셋에 따른 안티앨리어싱뿐이며(구버전은 JS가 남긴 인라인 폭 때문에 인쇄 시 좌표가 창 크기에 따라 달라졌음, 신버전은 항상 x=0으로 결정적), 두 이미지를 육안 대조해 동일함을 확인.
- **테스트**: `test_app4.py`의 17b 항목을 배율 기반에서 반응형 계약 기반으로 전면 재작성 — 12가지 화면 크기(2560×1400 ~ 360×740)에서 ① 가로 넘침 0 ② 두 페이지 모두 화면 밖으로 안 나감 ③ transform 미적용 ④ 1280px 이상 2단 / 1024px 이하 1단 ⑤ 좌우 여백 3px 이내 동일(중앙 정렬) ⑥ **글꼴 크기가 화면 크기와 무관하게 항상 동일**(14px/16px — 축소가 사라졌다는 직접 증거)을 확인. 넓은 창·좁은 창 양쪽에서 타이핑·주사위 클릭이 정상 반영되는지도 확인. 추가로 인쇄 A4 기하 구조(210mm 페이지, 본문 2단, 요약본 2단)를 실측값으로 고정하는 가드를 신설해, 앞으로 화면 쪽 수정이 인쇄를 건드리면 즉시 실패하도록 함. 3회 연속 전체 통과, 네이티브 다이얼로그·페이지 에러 0건.

GM 세션 대시보드는 기존 디자인 유지.

  9. **(17차에서 얻은 교훈, 18~19차에서도 재확인)** 인라인 `onclick`/`oninput` 안에서 렌더 함수의 지역 변수를 계산식 형태로 참조하면 안 된다는 원칙 — 18차의 리소스 −/+ 버튼은 이 원칙을 지켜서 새로 작성했고, 19차에서도 재확인해 위반 사례가 없음을 확인함. 이후에도 "버튼을 눌러도 반응이 없다"는 신고가 들어오면 콘솔의 `ReferenceError` 여부부터 확인하는 것이 빠른 진단 경로.
  10. **(18차 신규 → 20~25차에 걸쳐 여섯 차례 조정, 현재 진행형)** 웹 시트가 210mm 고정 폭 "종이" 레이아웃이라 화면이 좁거나 낮으면 원래는 스크롤이 필요했음. 20차(가로 기준 자동 축소) → 21차(세로까지 포함해 스크롤바 자체를 없애려 함, 그 결과 평범한 노트북 창에서도 배율이 40%대로 떨어져 가독성 저하) → 22차(데스크톱은 최소 0.85배를 보장하고 모자라면 스크롤 허용, 모바일은 기존처럼 가로 폭 100% 우선) → 23차(창에 여유가 있으면 최대 1.75배까지 확대 허용하되, 데스크톱 배율 기준을 가로 폭 하나로 단순화하고 세로 스크롤은 다시 허용) → 24차(23차 결과를 실제로 본 사용자가 큰 세로 스크롤량에 대해 "완전 제거"를 선택 → 데스크톱 배율 기준을 다시 가로·세로 중 더 빡빡한 쪽으로 되돌림, 1.75배 상한 자체는 유지) → 25차("배율(크기)"과는 별개로, 축소된 콘텐츠가 컨테이너보다 좁게 남을 때 그 여백이 중앙 정렬되지 않고 오른쪽 한쪽에만 쌓이는 문제를 발견해 수정 — 트레이드오프가 아니라 순수 버그였으므로 사용자에게 다시 묻지 않고 바로 반영)로 이어지며 "잘림 없음"·"가독성"·"큰 화면 활용"·"여백의 고른 분배" 사이의 균형점을 계속 조정해온 항목. 현재(25차) 기준으로는 창이 가로·세로 모두 넉넉할 때만 확대되고, 가로만 넓고 세로가 보통인 실제 모니터에서는 22차와 사실상 같은 크기(스크롤 없음, 큰 화면의 여백은 활용 못함)로 돌아간 상태 — "여백을 활용한 확대"와 "스크롤 없음"은 서로 대체 불가능한 트레이드오프라는 점이 이번에 구체적 수치로 확인됨. 다만 어느 쪽을 택하든 "축소된 콘텐츠 주변 여백은 항상 중앙 정렬된다"는 25차의 수정은 공통으로 적용됨. → **26차에서 이 항목은 해결된 것으로 본다**: 트레이드오프의 원인이 "화면과 인쇄가 하나의 기하 구조를 공유한다"는 데 있었으므로, 둘을 분리하자 "확대냐 스크롤이냐"라는 양자택일 자체가 사라짐(화면은 반응형으로 리플로우, 인쇄는 A4 고정). 남은 성질은 "세로 스크롤은 일반 웹 페이지처럼 정상적으로 발생한다"는 것 하나뿐이며, 이는 트레이드오프가 아니라 웹 레이아웃의 기본 동작임.
  11. **(18차에서 제기 → 19차에서 해결)** 마스터 비밀 메모를 뒷면에 장식용으로라도 남길지 여부를 열어뒀었는데, 19차에서 사용자 요청으로 완전히 삭제하기로 확정됨. 실제 GM 메모 기능은 이번 결정과 무관하게 GM 세션 탭의 PIN 잠금 안에 그대로 있음.
  12. **(19차 신규)** 피로도 아이콘의 반원(◐) 글자가 브라우저에서 얇은 초승달 모양으로 깨지는 문제를 웹 버전에서는 원 전체 채움(●)으로 교체해 해결했는데, 이 글꼴 렌더링 문제가 동일한 mm 단위 방식을 쓰는 `character_sheet.html`/PDF 원본에도 있는지는 확인하지 않았음 — 실제 PDF 출력물에서도 이 아이콘이 이상하게 보인다면 알려주면 PDF 쪽도 동일하게 고칠 수 있음.
  13. **(20차 신규 → 20차 안에서 방향 확인 진행)** 사용자가 (a) 원본 룰북으로 연결되는 링크 추가, (b) 여러 GM이 각자 독립된 "방"(세션)을 만들고 초대 링크로 플레이어를 공유·초대하며, 아무도 없으면 자동 소멸하는 멀티플레이 구조를 검토 중이라고 언급함. `AskUserQuestion`으로 방향을 확인한 결과: (a)는 **외부 URL 연결** 방식으로 확정 — 다만 실제 연결할 URL 주소를 아직 못 받아서 대기 중. (b)는 **"설계부터 논의"**로 확정, 이어서 호스팅 방식("무료/저비용 옵션 추천")과 실시간 공유 범위("캐릭터 시트 전체")까지 확인 완료 — 이를 반영해 Supabase 기반 아키텍처 설계 제안서를 별도 문서(`claude/멀티플레이_방_시스템_설계.md`)로 작성해 전달함. 문서에는 데이터 모델, GM 비밀정보 서버단 보호 원칙, 방 생명주기, 무료 티어 한도 등을 정리했고, 자동 삭제 타이밍·플레이어 구분 방식·방당 인원 규모·Supabase 가입 주체 확인 등 실제 구현 착수 전 확인이 필요한 항목을 문서 끝에 남겨둠 — 아직 실제 코드 구현은 시작하지 않음.
  14. **(21차 신규 → 22차에서 해결)** 21차에서 "스크롤바 절대 금지"를 우선시한 결과, 세로 공간이 부족한 창에서는 시트가 상당히 작게(약 40%대) 줄어들 수 있었음 — 실제로 사용자가 "화면 비율이랑 폰트가 전체적으로 너무 작아서 보기가 힘들어"라고 피드백을 줘서, 22차에서 최소 가독 배율(0.85)을 두고 그 아래로는 스크롤을 허용하는 절충안으로 조정함(자세한 내용은 22차 개정 항목 참고).
